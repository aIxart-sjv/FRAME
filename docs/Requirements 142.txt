# REQUIREMENT 1 — SENTINEL-2 DATA ACQUISITION

## 1. NTRO requirement

The PS requires FRAME to operate on **medium-resolution satellite imagery, specifically Sentinel-2 imagery**, and transform it into a higher-resolution analytical product.

The practical acquisition requirement is therefore:

> Obtain suitable Sentinel-2 imagery for a specified area and date, preferably Level-2A surface-reflectance data, together with the metadata and quality information required for reproducible preprocessing and downstream analysis.

This sounds trivial, but for a research-grade system the acquisition layer has to preserve:

* acquisition date/time
* tile/product identity
* spatial footprint
* CRS
* resolution
* band metadata
* radiometric information
* cloud information
* scene classification
* source/provenance
* original product identifiers

The acquisition layer should therefore **not simply download a JPEG/PNG or a visually rendered Sentinel-2 image**.

FRAME needs the actual multispectral raster data.

---

# 2. What Sentinel-2 data actually contains

Sentinel-2 MSI provides **13 spectral bands**:

| Band | Central wavelength approx. | Native resolution |
| ---- | -------------------------: | ----------------: |
| B1   |                     443 nm |              60 m |
| B2   |                     490 nm |              10 m |
| B3   |                     560 nm |              10 m |
| B4   |                     665 nm |              10 m |
| B5   |                     705 nm |              20 m |
| B6   |                     740 nm |              20 m |
| B7   |                     783 nm |              20 m |
| B8   |                     842 nm |              10 m |
| B8A  |                     865 nm |              20 m |
| B9   |                     945 nm |              60 m |
| B10  |                    1375 nm |              60 m |
| B11  |                    1610 nm |              20 m |
| B12  |                    2190 nm |              20 m |

Bhoonidhi's Sentinel-2 documentation confirms the 13-band configuration: four bands at 10 m, six at 20 m and three at 60 m. ([Bhoonidhi][1])

### Critical FRAME detail

**B10 should not be counted as one of our 12 L2A analysis bands.**

For Sentinel-2 Level-2A surface-reflectance processing, B10 is not included in the L2A surface-reflectance product because its atmospheric absorption characteristics make it unsuitable for the surface-reflectance product.

Therefore our technical specification should say:

> **12 usable Sentinel-2 L2A spectral bands: B1–B9, B8A, B11 and B12.**

Not:

> "all 13 Sentinel-2 bands."

This distinction needs to be maintained throughout the project.

# 3. What are the actual acquisition choices?

There are four relevant categories.

### A. Copernicus Data Space Ecosystem

Official European source.

### B. Sentinel Hub / commercial EO APIs

Industry-oriented access layer.

### C. Bhoonidhi / NRSC / ISRO

# 4. GLOBAL / OFFICIAL SOLUTION — Copernicus Data Space

The primary authoritative source for Sentinel-2 is the Copernicus ecosystem.

The current Copernicus Data Space Ecosystem exposes a STAC catalogue specifically for machine-readable EO data discovery.

Its current STAC endpoint is:

`https://stac.dataspace.copernicus.eu/v1/`

The catalogue includes a dedicated:

`sentinel-2-l2a`

collection. ([Data Space Documentation][2])

The API supports:

* spatial search
* temporal search
* cloud-cover filtering
* CQL2 filtering
* sorting
* field selection
* collection filtering
* GeoJSON intersection queries

For example, a search can constrain:

```text
Collection:
Sentinel-2 L2A

AOI:
Polygon

Date:
2026-01-01 → 2026-03-01

Cloud cover:
< 10%

Output:
STAC metadata + asset references
```

Copernicus explicitly documents filtering Sentinel-2 L2A using `eo:cloud_cover`. ([Data Space Documentation][2])

---

# 5. Why STAC matters to FRAME

STAC is more than a convenient API.

It gives us a **standardized machine-readable description of an Earth-observation asset**.

Instead of:

```text
Download random Sentinel file
↓
Try to figure out what it is
```

we can do:

```text
AOI
+
Date range
+
Cloud threshold
+
Sentinel-2 L2A
↓
STAC search
↓
Candidate products
↓
Select product
↓
Retrieve required assets
```

This makes FRAME reproducible.

It also means the acquisition layer can later be replaced without redesigning the entire pipeline.

---

# 6. Copernicus Data Space — advantages

### Strengths

**Authoritative source**

Sentinel-2 is an ESA/Copernicus mission, so this is the natural reference source.

**Current**

The Data Space ecosystem is actively maintained.

**Machine-readable**

STAC is designed for programmatic EO discovery.

**Spatial filtering**

We can search by AOI rather than manually browsing tiles.

**Temporal filtering**

We can request specific acquisition windows.

**Cloud filtering**

Very useful for automatic dataset creation.

**Metadata**

STAC gives structured metadata.

**Scalable**

Suitable for building automated data pipelines.

Copernicus also provides Python-oriented API access alongside HTTP APIs. ([Data Space Documentation][3])

---

# 7. Copernicus Data Space — limitations

The biggest limitation isn't the data itself.

It is **pipeline complexity**.

A research pipeline has to handle:

* authentication where required
* asset retrieval
* large products
* multiple bands
* SAFE/product structures
* spatial subsetting
* memory management
* network failures
* retries
* local caching

If we download complete Sentinel-2 products for every training sample, storage requirements become unnecessarily large.

Therefore:

> FRAME should search the catalogue first and retrieve only the required spatial/band data whenever practical.

---

# 8. GLOBAL INDUSTRY SOLUTION — Sentinel Hub

Sentinel Hub is an industry-grade EO data access/processing platform.

Its current documentation exposes Sentinel-2 L2A through APIs and allows users to specify exactly what data they want. ([Data Space Documentation][4])

It supports:

* Sentinel-2 L1C
* Sentinel-2 L2A
* catalogue searches
* cloud filtering
* custom processing
* band selection
* spatial output
* GeoTIFF
* derived products
* metadata

The API can return exactly the requested bands rather than requiring FRAME to process an entire scene.

---

# 9. Why industry uses this approach

The important idea is:

> **Don't necessarily move the entire satellite product to your application. Move only the information you need.**

For example:

```text
AOI
↓
Sentinel Hub
↓
B2/B3/B4/B8
+
B5/B6/B7/B8A/B11/B12
↓
Cloud masking / processing
↓
FRAME
```

This can dramatically simplify operational processing.

Sentinel Hub also supports commercial imagery such as PlanetScope, SkySat and Maxar products under appropriate licensing, demonstrating how the same API abstraction can span multiple EO sources. ([Sentinel Hub][5])

# 11. INDIAN SOLUTION — Bhoonidhi

This is the most important Indian acquisition platform.

Bhoonidhi is operated by **NRSC/ISRO** and describes itself as ISRO's EO data hub.

Its current portal provides access to remote-sensing archives from **47 satellites**, including Indian and foreign sensors, and specifically facilitates regional distribution of Sentinel and Landsat data in India. ([Bhoonidhi][6])

Bhoonidhi provides:

* browse/order
* visualization
* download
* satellite data archive
* Sentinel-1/2 access
* Indian satellite products
* API access
* STAC-based search

This makes it particularly relevant to our proposed **Indian-domain evaluation**.

---

# 12. Bhoonidhi API — important new development

This is not just a web portal anymore.

Bhoonidhi now provides a documented API.

The API supports:

```text
Authentication
    ↓
Search
    ↓
STAC catalogue
    ↓
Filter
    ↓
Product selection
    ↓
Download
```

Its search API is STAC-based and supports:

* collections
* datetime
* spatial intersection
* bounding box
* filters
* limits
* CQL2-style filtering. ([Bhoonidhi][7])

The documented endpoint structure includes:

```text
/auth/token
/data/search
/download
```

and supports authenticated programmatic access. ([Bhoonidhi][7])

That makes Bhoonidhi considerably more interesting for FRAME than merely being an Indian website from which someone manually downloads imagery.

---

# 13. Bhoonidhi has a particularly important Sentinel advantage

ISRO states that Bhoonidhi serves as a **regional hub for Sentinel-1 and Sentinel-2 data**, with Sentinel data available for the Indian subcontinent region. ([ISRO][8])

Bhoonidhi's older browse/order documentation explains that Sentinel series data are made available through the ESA source while Bhoonidhi provides the regional distribution interface. ([Bhoonidhi][9])

Therefore:

> Bhoonidhi should not be described as an independent Sentinel-2 sensor/data-generation system.

It is better described as:

> **An Indian EO data dissemination and access layer, including regional Sentinel-2 distribution.**

That distinction matters in the final report.

# 14. Bhoonidhi's advantage for FRAME

### Role 1 — Sentinel-2 acquisition

We can use it as an Indian-access route to Sentinel imagery.

### Role 2 — Indian validation ecosystem

That fits our emerging research direction.

# 18. Why PySTAC Client is particularly appropriate

Copernicus itself demonstrates Python access to its STAC endpoint using `pystac_client`. ([Data Space Documentation][10])

The workflow is essentially:

```python
from pystac_client import Client

catalog = Client.open(
    "https://stac.dataspace.copernicus.eu/v1"
)

search = catalog.search(
    collections=["sentinel-2-l2a"],
    intersects=aoi,
    datetime="2026-01-01/2026-03-01",
    query={"eo:cloud_cover": {"lte": 10}}
)

items = list(search.items())
```

This is almost exactly the acquisition abstraction FRAME needs.

# 21. Cloud filtering

A simple first-stage rule can be:

```text
scene cloud cover ≤ 10%
```

But this should **not** be treated as the final cloud mask.

Why?

Because scene-level cloud cover doesn't tell us whether clouds are sitting directly over the specific AOI.

Therefore:

```text
Stage 1:
Scene-level cloud filter

        ↓

Stage 2:
AOI-specific QA

        ↓

Stage 3:
SCL/cloud/shadow masking
```

This is much more robust.

Copernicus' STAC API explicitly supports filtering Sentinel-2 L2A using `eo:cloud_cover`. ([Data Space Documentation][2])

---

# 22. Important acquisition mistake to avoid

Do not do this:

```text
Search Sentinel-2
↓
Take lowest cloud-cover scene
↓
Train
```

That can introduce dataset bias.

For training and validation, we need to consider:

* geographic diversity
* seasons
* land-cover diversity
* atmospheric conditions
* cloud/shadow patterns
* acquisition dates
* sensor processing versions

Otherwise the model may simply learn the distribution of our training locations.

This becomes particularly important because our proposed research question involves **geographic generalisation**.

# 26. What is actually difficult?

Not finding Sentinel-2.

The actual engineering problems are:

### 1. Reproducibility

Can we always identify exactly which Sentinel product generated the FRAME result?

### 2. Data quality

Can we automatically reject unsuitable scenes?

Can we avoid scenes that are technically low-cloud but unusable over our target?

### 4. Band consistency

Can we guarantee the expected 12-band set?

### 5. Metadata preservation

Can downstream outputs still be geospatially correct?

### 6. Dataset diversity

Can our training/validation data avoid geographic bias?

### 7. Provider independence

Can FRAME switch between Copernicus and Bhoonidhi without rewriting the pipeline?

These are legitimate engineering challenges.

# SIH26142 — FRAME

## REQUIREMENT 2 — MULTISPECTRAL PREPROCESSING & HARMONISATION

This requirement is substantially more important than Requirement 1.

The acquisition problem is basically solved. The preprocessing problem is where **Sentinel-2's heterogeneous spatial resolutions, radiometry, QA information, registration and band relationships have to be converted into a consistent input representation for SR**.

And there is an important distinction we need to maintain:

> **Harmonisation is not the same thing as super-resolution.**

Existing systems already solve parts of this problem, so FRAME needs to be precise about what it actually does.

---

# 1. What NTRO requires

The PS expects a system capable of transforming:

> **10 m Sentinel-2 imagery into a sharper sub-4 m product while maintaining spectral and geospatial consistency.**

For that to work, the input cannot simply be:

```text
B1
B2
B3
...
B12
```

with arbitrary resizing.

Sentinel-2 L2A contains the useful 12-band set at **three different native resolutions**:

```text
10 m:
B2 B3 B4 B8

20 m:
B5 B6 B7 B8A B11 B12

60 m:
B1 B9
```

B10 is excluded from L2A surface-reflectance processing.

Sen2Cor's current documentation confirms that L2A products retain the multi-resolution structure: 10 m, 20 m and 60 m products, with surface reflectance and quality information. ([STEP][1])

Therefore FRAME needs a **common representation** before the SR network can process all 12 channels together.

---

# 2. The actual preprocessing problem

There are at least seven separate operations.

## 2.1 Radiometric conversion

Sentinel-2 L2A data are stored as quantized digital numbers.

The conversion must account for the processing baseline's radiometric offset.

This is particularly important because Sentinel-2 processing baseline 04.00 introduced a radiometric offset to preserve negative surface-reflectance values.

ESA documents the conversion as:

> `L2A_SR = (L2A_DN + BOA_ADD_OFFSET) / QUANTIFICATION_VALUE`

For the relevant newer processing baselines, the practical conversion is documented as:

> `(DN - 1000) / 10000`

rather than simply:

> `DN / 10000`. ([STEP Forum][2])

### This is important for FRAME.

If we blindly divide every L2A DN by 10,000, we can introduce radiometric errors.

Therefore the preprocessing code should read the product's metadata and apply the appropriate baseline/offset rather than hard-coding one formula.

---

# 3. Atmospheric correction

We are proposing to start from:

> **Sentinel-2 L2A**

rather than L1C.

Why?

L2A is already surface-reflectance corrected.

Sen2Cor performs:

* atmospheric correction
* terrain correction
* cirrus correction where applicable
* surface-reflectance generation
* aerosol optical thickness estimation
* water-vapour estimation
* scene classification
* cloud/snow probability generation. ([STEP][3])

Therefore:

### FRAME should NOT perform its own atmospheric correction by default.

That would duplicate a mature ESA processing chain.

---

# 4. Scene Classification / cloud / shadow masking

L2A gives us the **Scene Classification Layer (SCL)**.

Current Sen2Cor documentation describes classes covering:

* no data
* saturated/defective
* cast shadow
* vegetation
* non-vegetated
* water
* unclassified
* medium-probability cloud
* high-probability cloud
* thin cirrus
* snow/ice

and associated cloud/snow probability information. ([STEP][4])

The current Sen2Cor version has also improved cloud-shadow detection, topographic/cast-shadow handling and other classification behaviour. ([STEP][1])

### FRAME preprocessing should therefore use SCL.

We should mask at least:

```text
NoData
Saturated/defective
Cloud shadow
Cloud
Cirrus
Snow/ice
```

with the exact treatment of ambiguous/unclassified pixels determined experimentally.

---

# 5. Important distinction: masking vs deleting

We should **not simply delete cloudy pixels from the raster**.

That would destroy spatial correspondence.

Instead:

```text
valid pixels
→ retained

invalid pixels
→ validity mask
```

So FRAME maintains:

```text
12-band data
+
validity mask
```

through the pipeline.

This is important for both:

* training
* inference
* downstream analysis.

---

# 6. Native-resolution problem

Now we reach the central issue.

Suppose one Sentinel-2 patch contains:

```text
B2: 10m
B3: 10m
B4: 10m
B5: 20m
B6: 20m
B7: 20m
B8: 10m
B8A: 20m
B11: 20m
B12: 20m
B1: 60m
B9: 60m
```

A CNN cannot simply receive different tensor dimensions for each channel.

Therefore we need:

```text
10m
20m → common grid
60m → common grid
```

before creating the final tensor.

---

# 7. Existing solution #1 — ordinary resampling

The simplest solution is:

```text
20m → 10m
60m → 10m
```

using interpolation.

Possible methods:

* nearest neighbour
* bilinear
* bicubic
* Lanczos

SNAP has an explicit Resampling operator for converting a multi-size product to a common target size. 

### But this does NOT create new spatial information.

If:

```text
20m → 10m
```

with bicubic interpolation, we now have 10 m pixels mathematically, but the original information content is still 20 m.

This distinction is critical.

ESA's documentation explicitly distinguishes ordinary resampling from learned super-resolution: resampling changes pixel spacing but does not improve spatial detail. ([STEP Forum][5])

---

# 8. Existing solution #2 — Sen2Res

ESA's older **Sen2Res** approach is more interesting.

Sen2Res uses the four native 10 m Sentinel-2 bands to infer spatial information for lower-resolution bands.

Its objective is essentially:

```text
10m RGB/NIR
       ↓
learn shared spatial information
       ↓
20m/60m bands
       ↓
10m output
```

ESA describes Sen2Res as a processor that enhances Sentinel-2 products to 10 m while preserving reflectance. ([STEP][6])

This is an important historical predecessor.

It demonstrates that:

> **Multispectral harmonisation + spatial detail transfer was already an established Sentinel-2 research problem before deep 2.5 m SR.**

---

# 9. Existing solution #3 — DSen2

DSen2 is another major predecessor.

Its contribution was learning to super-resolve Sentinel-2's lower-resolution bands to the 10 m grid using the higher-resolution bands as spatial guidance.

The underlying idea is:

```text
10m bands
+
20m bands
+
60m bands
↓
learned multispectral reconstruction
↓
10m multispectral product
```

The fundamental concept is described in the DSen2 work on super-resolving multiresolution multispectral imagery. ([DOI][7])

This is highly relevant to FRAME because our pipeline is essentially taking that problem one step further:

```text
native multi-resolution S2
        ↓
common representation
        ↓
2.5m SR
```

---

# 10. Existing solution #4 — SEN2SR

The current state of the art goes significantly further.

SEN2SR works with:

* 10 m RGB/NIR
* 20 m red-edge/SWIR
* 2.5 m output

and specifically addresses the challenge of making the training data match Sentinel-2's spectral and spatial characteristics. ([ScienceDirect][8])

Its architecture incorporates a **low-frequency hard constraint** at the end of the SR network.

Conceptually:

```text
Input
 ↓
SR network
 ↓
high-frequency reconstruction
 ↓
low-frequency constraint
 ↓
output
```

The purpose is to prevent the model from freely changing the low-frequency content of the original observation.

This is directly relevant to FRAME.

---

# 11. Existing solution #5 — SEN2NEON

SEN2NEON is particularly important for our preprocessing decisions.

The benchmark takes:

> original Sentinel-2 L2A observations

and creates an aligned common representation containing:

> **12 Sentinel-2-equivalent bands on a common 10 m grid**

before pairing them with a 2.5 m AVIRIS-NG-derived reference. ([GitHub][9])

That is almost exactly the type of input representation FRAME needs.

But there is an important caveat:

> SEN2NEON's 10 m stack is a **convenience aligned product**; it does not mean that the original B1/B9 observations were physically measured at 10 m.

The benchmark itself says that the convenience LR product does not preserve the original separate native grids. ([GitHub][9])

That distinction should also appear in our documentation.

---

# 12. Existing solution #6 — SNAP S2 Super Resolution

Current SNAP also provides an S2 Super-Resolution processor.

It:

* accepts L1C/L2A
* super-resolves selected 10/20 m bands
* produces a 5 m output
* can optionally include the 60 m bands
* but the 60 m bands are only bicubically resampled rather than learned SR. 

The currently documented super-resolved bands are:

```text
B2
B3
B4
B5
B6
B7
B8
B8A
B11
B12
```

while B1 and B9 can be included through resampling. 

This creates an important distinction from our proposed 12-band architecture.

---

# 13. Global/industry landscape

The current global stack is therefore roughly:

| System              | Input handling        | Output         | Key characteristic            |
| ------------------- | --------------------- | -------------- | ----------------------------- |
| Standard resampling | 10/20/60m             | common grid    | interpolation                 |
| Sen2Res             | multi-resolution S2   | 10m            | multispectral detail transfer |
| DSen2               | multi-resolution S2   | 10m            | learned SR                    |
| SNAP S2 SR          | 10/20m + optional 60m | 5m             | learned SR                    |
| SEN2SR              | 10/20m                | 2.5m           | modern SR + consistency       |
| SEN2NEON            | 12-band S2            | 2.5m benchmark | aligned real HR reference     |

This tells us something important.

---

# 14. What FRAME should NOT do

We should **not** implement:

```text
20m → bicubic → 10m
60m → bicubic → 10m
↓
pretend all 12 bands are native 10m
↓
4× SR
```

without clearly acknowledging what happened.

That would create an awkward two-stage reconstruction:

```text
60m
↓
interpolation
↓
10m
↓
learned SR
↓
2.5m
```

and could amplify artefacts.

---

# 15. The better FRAME architecture

There are two possible architectures.

## Option A — explicit harmonisation

```text
10m bands
        │
20m → learned/controlled harmonisation
        │
60m → learned/controlled harmonisation
        │
        ▼
12-band 10m representation
        │
        ▼
4× SR
        │
        ▼
2.5m
```

## Option B — multi-resolution model

```text
10m bands ────────┐
20m bands ────────┼──→ multi-resolution SR network → 2.5m
60m bands ────────┘
```

### Option B is scientifically cleaner.

But it is considerably harder.

---

# 16. What current SEN2SR suggests

Modern SEN2SR effectively demonstrates that the model can reason about the different spatial resolutions rather than treating everything as equally observed at 10 m.

Its current framework super-resolves:

> 10 m RGB/NIR and 20 m red-edge/SWIR

to 2.5 m. ([ScienceDirect][8])

However, the full 12-band story still requires careful handling of B1 and B9, whose native resolution is 60 m.

This creates an important FRAME design question:

> **Should B1/B9 actually participate in the 2.5 m reconstruction, or should they remain lower-resolution contextual channels?**

We should **not decide this by intuition**.

It needs an experiment.

---

# 17. This gives us a potentially important experiment

Train/evaluate:

### Model A

```text
10m bands only
```

### Model B

```text
10m + resampled 20m bands
```

### Model C

```text
10m + 20m + resampled 60m bands
```

Then compare:

* spectral fidelity
* spatial fidelity
* downstream classification
* stability
* computational cost

If B1/B9 add useful information, keep them.

If they mainly inject interpolation artefacts/noise, we should not force them into the SR head merely so we can say "12 bands."

---

# 18. Indian solution

Indian work exists here too.

A 2025 Remote Sensing Letters paper from researchers associated with **NRSC/ISRO** developed a guided CNN super-resolution approach for satellite spectral-band enhancement.

It generated a 5 m SWIR product for Resourcesat LISS-4 using lower-resolution SWIR information and higher-resolution bands, and the authors also applied the approach to Sentinel-2 to super-resolve lower-resolution bands to **10 m**. The data were made available through Bhoonidhi. ([Taylor & Francis Online][10])

This is very relevant.

It proves:

> Indian researchers are already working on learned multispectral/spectral-band SR.

Therefore we cannot claim:

> "India has not addressed multispectral Sentinel-2 super-resolution."

But the Indian work we found does **not** establish the same complete problem as FRAME:

```text
12-band L2A
→ 2.5m
→ stability evidence
→ downstream analysis
→ geographic robustness
```

That distinction is important.

---

# 19. Indian preprocessing ecosystem

The Indian advantage is mainly **data access and domain-specific evaluation**, rather than a unique preprocessing algorithm.

Bhoonidhi gives us access to Indian EO data and Sentinel distribution, which can support:

* Indian scene selection
* validation
* domain-specific testing
* cross-sensor experiments

rather than forcing us to invent an Indian preprocessing algorithm.

# 21. Recommended preprocessing architecture

I recommend we currently specify:

```text
Sentinel-2 L2A
      ↓
Read metadata + processing baseline
      ↓
Radiometric conversion
      ↓
SCL / QA masking
      ↓
NoData / invalid-value handling
      ↓
Native-grid extraction
      ↓
Co-registration to common spatial frame
      ↓
Multiresolution harmonisation
      ↓
12-channel tensor
      ↓
SR model
```

But I would **not yet freeze the exact 20m/60m resampling algorithm**.

That needs to be decided after Requirement 4, because the optimal preprocessing is coupled to the SR architecture.

# 23. Resampling recommendation

For the **initial baseline**, use:

### 20m → 10m

**Bilinear**

### 60m → 10m

**Bilinear**

but only as an input harmonisation baseline.

Why not nearest neighbour?

Because it creates block-like discontinuities.

Why not bicubic immediately?

Because we should establish a simple baseline before optimizing.

However, this does **not** mean these interpolated values are treated as new information.

---

# 24. More important: preserve native-resolution provenance

FRAME should retain metadata describing the source resolution of every channel.

For example:

```python
source_resolution = {
    "B1": 60,
    "B2": 10,
    "B3": 10,
    "B4": 10,
    "B5": 20,
    "B6": 20,
    "B7": 20,
    "B8": 10,
    "B8A": 20,
    "B9": 60,
    "B11": 20,
    "B12": 20
}
```

This is important because after harmonisation every channel has the same tensor dimensions, but they **do not have the same original information resolution**.

---

# 25. Another important point: don't call this "native 10m"

After harmonisation:

Incorrect:

> "12 native 10 m Sentinel-2 bands"

Correct:

> **"12-band Sentinel-2 L2A stack resampled/aligned to a common 10 m computational grid."**

This distinction should appear throughout FRAME documentation.

# Requirement 2 conclusion

The key conclusion is:

> **FRAME should not treat preprocessing as "resize everything to 10 m."**

The correct conceptual pipeline is:

```text
SENTINEL-2 L2A
      ↓
Radiometric interpretation
      ↓
SCL / QA masking
      ↓
Native-resolution band extraction
      ↓
10/20/60m spatial harmonisation
      ↓
12-channel common computational grid
      ↓
4× SR
      ↓
2.5m reconstructed product
```

But **the exact harmonisation strategy is deliberately not frozen yet**.

The next requirement — **Requirement 3: Paired LR–HR Dataset Creation** — is where we determine what data FRAME should actually train on, because the degradation/harmonisation strategy cannot be designed correctly without understanding the available real LR-HR pairs.

That section will compare **SEN2NEON, SEN2NAIPv2, SEN2VENµS, MuS2, OpenSR-Test, synthetic degradation, Indian reference possibilities and exactly what should be TRAIN vs VALIDATION vs TEST**.

# SIH26142 — FRAME

## REQUIREMENT 3 — PAIRED LR–HR DATASET CREATION

This is the first requirement where the research materially changes the design of FRAME.

The central problem is not:

> "Can we find satellite images?"

It is:

> **How do we obtain training pairs where the low-resolution input genuinely represents what Sentinel-2 observes, while the high-resolution target represents the information we want the model to reconstruct?**

This matters because Sentinel-2 SR is an **ill-posed inverse problem**. Many different HR images can produce very similar LR observations. A model can therefore learn to generate visually convincing details that are not actually supported by the Sentinel-2 measurement.

Recent SEN2NAIP and SEN2SR work directly identifies this issue. ([Nature][1])

---

# 1. NTRO requirement

The PS explicitly requires:

* paired dataset creation
* training of a deep-learning SR model
* accuracy assessment
* validation against high-resolution references.

Therefore FRAME needs three conceptually different data relationships:

```text
TRAINING
LR Sentinel-2-like input
        ↕
HR reference

VALIDATION
Real LR Sentinel-2
        ↕
Independent HR reference

OPERATIONAL INFERENCE
Real Sentinel-2
        ↓
FRAME
        ↓
2.5 m reconstruction
```

The mistake would be treating all three as the same dataset.

They should be deliberately separated.

---

# 2. The fundamental dataset problem

There are two major ways of constructing SR datasets.

## Approach A — Synthetic degradation

Start with HR imagery:

```text
HR
↓
blur
↓
downsample
↓
noise
↓
LR
```

Then train:

```text
LR → HR
```

### Advantage

We can generate enormous amounts of training data.

### Problem

The synthetic LR image may not behave like real Sentinel-2.

---

## Approach B — Cross-sensor real pairs

Find:

```text
Sentinel-2 LR
+
same/similar-date HR sensor
```

For example:

```text
Sentinel-2 10m
+
NAIP 2.5m
```

or:

```text
Sentinel-2
+
AVIRIS-NG-derived 2.5m
```

### Advantage

The LR image is an actual satellite observation.

### Problem

The sensors differ in:

* spectral response
* spatial PSF
* acquisition time
* viewing geometry
* atmospheric conditions
* radiometric calibration.

Therefore the HR image isn't automatically a perfect Sentinel-2 ground truth.

---

# 3. SEN2VENµS — one of the foundational datasets

SEN2VENµS was one of the first major publicly available real paired datasets for Sentinel-2 SR.

It pairs:

* Sentinel-2 10 m / 20 m
* VENµS 5 m
* same day
* spatially registered
* cloud-free surface reflectance.

It covers:

* **29 locations**
* **132,955 patches**
* 256×256 pixels at 5 m.

It supports SR of **8 Sentinel-2 bands**:

```text
10m:
B2 B3 B4 B8

20m:
B5 B6 B7 B8A
```

The dataset does not provide 5 m HR references for B1/B9/B11/B12. ([DOI][2])

---

# 4. SEN2VENµS is extremely useful — but not enough for FRAME

### Strengths

* real Sentinel-2 LR
* real HR sensor
* same-day acquisition
* spatial registration
* large dataset
* open
* specifically created for SR

### Limitations

It only provides HR references for:

```text
B2 B3 B4 B5 B6 B7 B8 B8A
```

not all 12 L2A bands. ([Zenodo][3])

And the HR resolution is:

> **5 m**

not our desired 2.5 m.

Therefore:

### Verdict

**Excellent training resource for 10/20 m multispectral SR research.**

But:

> **Not sufficient as the sole training/validation dataset for FRAME's 12-band 2.5 m objective.**

---

# 5. SEN2NAIP — major development

SEN2NAIP was published in 2024 specifically to address the limitations of synthetic SR datasets.

It contains:

### Cross-sensor component

**2,851 Sentinel-2 / NAIP pairs**

with:

* Sentinel-2
* NAIP
* approximately 2.5 m HR
* ~1.46 km² coverage per pair.

The authors then learn a degradation model from these real pairs. ([Nature][1])

---

# 6. Why SEN2NAIP is more important than simply "another dataset"

The researchers don't simply do:

```text
NAIP
↓
bicubic
↓
S2-like
```

Instead, they model:

### Point-spread function

How the sensor blurs spatial information.

### Spectral alignment

How NAIP spectral measurements differ from Sentinel-2.

### Noise

How sensor noise behaves as a function of reflectance.

The paper represents the degradation conceptually as:

```text
NAIP
 ↓
spectral transformation
 ↓
PSF / blur
 ↓
downsampling
 ↓
noise
 ↓
S2-like image
```

This is much closer to a physically plausible Sentinel-2 degradation process than simply resizing an image. ([Nature][1])

---

# 7. SEN2NAIP synthetic dataset

Once the degradation model is learned, it can generate a much larger training dataset.

The original paper reports:

* 2,851 cross-sensor ROIs
* 17,657 synthetic ROIs
* 20,508 total ROIs
* approximately 35,314 synthetic images.

The synthetic data are generated from NAIP using the learned degradation process. ([Nature][1])

This solves a major problem:

> Real simultaneous LR-HR pairs are expensive and geographically limited.

Synthetic degradation gives us scale.

---

# 8. But SEN2NAIP has a major limitation

The original SEN2NAIP training focus is:

> **RGB + NIR**

rather than all 12 Sentinel-2 L2A bands.

The paper explicitly states that its Sentinel-2 component focuses on the 10 m RGBNIR bands. ([Nature][1])

So:

```text
B2 B3 B4 B8
```

rather than:

```text
B1 B2 B3 B4 B5 B6 B7 B8 B8A B9 B11 B12
```

Therefore:

> **SEN2NAIP cannot alone provide FRAME's full 12-band training target.**

---

# 9. SEN2NAIPv2

The current SEN2SR ecosystem has expanded SEN2NAIP.

The current SEN2NAIPv2 dataset contains roughly **61k–62k LR-HR pairs**, depending on the specific release/counting convention. The SEN2SR paper reports **61,282** training pairs, while the current dataset distribution reports **62,242 pairs**. ([DOI][4])

The important point is the scale:

> **~62,000 synthetic RGBN 2.5 m/10 m pairs.**

Its degradation chain is:

```text
NAIP HR
 ↓
Gaussian blur
 ↓
bilinear downsampling
 ↓
reflectance harmonisation
 ↓
noise
 ↓
S2-like LR
```

The current v2 dataset uses a retrained U-Net harmonisation model. ([Hugging Face][5])

---

# 10. This creates a major lesson for FRAME

The most important result from SEN2NAIP's technical validation is that:

> **A model can perform well on synthetic data while performing substantially differently on real cross-sensor data.**

Their experiments found that models trained without realistic harmonisation could behave almost like bilinear interpolation when tested on real Sentinel-2 imagery, while degradation/harmonisation-aware training produced substantially different high-frequency reconstruction behaviour. ([Nature][1])

Therefore:

### We cannot do:

```text
Synthetic training
↓
high PSNR
↓
declare success
```

We need:

```text
Synthetic training
↓
real cross-sensor validation
↓
independent benchmark
```

This becomes a core FRAME principle.

---

# 11. SEN2SR confirms this dataset strategy

The current SEN2SR paper uses:

### Training

* **SEN2NAIPv2-synthetic**
* **CloudSEN12**

### Validation

* **SEN2NAIPv2-cross-sensor**
* **OpenSR-Test**

The paper explicitly describes this training/validation separation. ([DOI][4])

This is extremely useful because it gives us a current state-of-the-art experimental template.

---

# 12. CloudSEN12 — why is a cloud dataset involved?

CloudSEN12 is primarily a cloud/cloud-shadow semantic dataset, not an HR SR dataset.

It contains Sentinel-2 L1C/L2A imagery and cloud/shadow annotations. ([GitHub][6])

SEN2SR uses cloud-free data from this ecosystem as part of its training data preparation. ([DOI][4])

The broader lesson is:

> **Training data quality matters as much as dataset size.**

FRAME should not simply download millions of random Sentinel patches.

We need curated, valid, cloud-free training inputs.

---

# 13. SEN2NEON — the most important current dataset for FRAME

SEN2NEON is probably the most strategically important dataset we've found so far.

It provides:

* **2,269 tiles**
* 12 Sentinel-2-equivalent bands
* LR Sentinel-2 L2A
* canonical **2.5 m HR**
* AVIRIS-NG-derived reference
* 119 NEON acquisition assets
* 110 dates
* 2018–2024
* multiple land-cover types.

([GitHub][7])

---

# 14. Why SEN2NEON is different

The HR reference isn't simply an RGB aerial photograph.

AVIRIS-NG is hyperspectral.

The authors transform it to the **Sentinel-2 spectral response functions**.

So:

```text
AVIRIS-NG hyperspectral
        ↓
Sentinel-2 spectral response harmonisation
        ↓
12-band Sentinel-2-equivalent HR
        ↓
2.5 m reference
```

This is extremely valuable.

It means the target isn't merely:

> "an RGB image that visually resembles the scene."

It is:

> **a 12-band Sentinel-2-equivalent spectral reference.**

([GitHub][7])

---

# 15. SEN2NEON directly addresses our biggest weakness

Our original FRAME concept wanted:

> 12 bands → 2.5 m.

Previously, we thought that this might itself be a novelty.

It isn't.

SEN2NEON now directly provides:

> 12 bands → 2.5 m reference.

([GitHub][7])

Therefore:

### Novelty claim removed.

But:

### Validation opportunity added.

FRAME should almost certainly use SEN2NEON.

---

# 16. SEN2NEON's limitation

Its geography is tied to the **NEON network in the United States**.

Therefore:

```text
Great for:
scientific benchmark
12-band evaluation
2.5m evaluation
land-cover stratification

Not sufficient for:
Indian generalisation
Indian landscape robustness
Indian seasonal behaviour
```

This reinforces our emerging Indian-domain research direction.

---

# 17. OpenSR-Test

OpenSR-Test is currently one of the most important real-world SR evaluation frameworks.

It contains:

| Dataset     | Scale | Images | Geography/reference |
| ----------- | ----: | -----: | ------------------- |
| NAIP        |    ×4 |     62 | US                  |
| SPOT        |    ×4 |      9 | WorldStrat          |
| Venµs       |    ×2 |     59 | multiple            |
| Spain Crops |    ×4 |     28 | Spain               |
| Spain Urban |    ×4 |     20 | Spain               |

It is explicitly designed to minimize spatial/spectral misalignment. ([GitHub][8])

---

# 18. Why OpenSR-Test matters

Traditional evaluation asks:

> "How similar is my output to the HR image?"

OpenSR-Test expands the question into:

### Consistency

Does SR remain faithful to the input?

### Synthesis

What high-frequency information did it generate?

### Correctness

Does that information correspond to reality?

The project explicitly includes concepts such as:

* spectral distance
* hallucination rate
* semantic accuracy
* perceptual similarity. ([OpenSR][9])

This fits FRAME extremely well.

---

# 19. OpenSR-Test should NOT be our training dataset

This is important.

Its purpose is primarily:

> **benchmarking/evaluation.**

We should not casually merge its test imagery into training.

Otherwise:

```text
train on benchmark
↓
test on benchmark
↓
invalid result
```

---

# 20. MuS2

MuS2 is a different problem.

It targets **multi-image super-resolution (MISR)**.

Its benchmark contains:

* **91 scenes**
* > 3,200 km²
* at least **14 Sentinel-2 images per scene**
* one WorldView-2 HR reference.

([Nature][10])

The benchmark evaluates approximately 3× magnification and provides protocols for comparing the output to the WV-2 reference.

---

# 21. Should FRAME use MuS2?

Potentially, but with a clear distinction.

FRAME is currently designed as:

> **single-image SR**

not:

> multi-image temporal SR.

Therefore MuS2 should **not be a primary training dataset**.

It can be a supplementary benchmark for answering:

> How does single-image FRAME compare with a multi-image SR setting?

But that's beyond our core PS.

### Verdict:

**Secondary evaluation/reference, not core training.**

---

# 22. WorldStrat / SPOT

OpenSR-Test's SPOT subset originates from WorldStrat.

It provides:

* Sentinel-2 LR
* SPOT HR
* 2.5 m HR
* RGBNIR
* urban/crops/bare-soil coverage.

OpenSR-Test currently uses 9 SPOT images for its benchmark. ([GitHub][8])

This is valuable because it gives us:

> A real cross-sensor 2.5 m test case that isn't simply NAIP.

That reduces dependence on one reference sensor.

---

# 23. Dataset comparison

Here is the important comparison for FRAME.

| Dataset        |        Real S2 LR |     Real HR |   2.5m HR |     12 bands |       Scale | Best role             |

---

# 24. This gives us the first real FRAME dataset strategy

We should **not** try to create one giant custom dataset from scratch.

Instead:

## Tier 1 — Training

### SEN2NAIPv2 synthetic

Main large-scale training source.

Why?

* huge
* 2.5 m target
* realistic degradation
* S2-like LR
* mature degradation model.

([Hugging Face][5])

---

# 25. Tier 2 — supplementary training

### SEN2VENµS

Use it to expose the model to:

* real Sentinel-2 observations
* real HR reference
* multispectral bands
* simultaneous cross-sensor acquisition.

But its target is 5 m and only 8 bands.

Therefore:

> **Do not pretend SEN2VENµS trains the final 12-band 2.5 m task directly.**

It is supplementary.

---

# 26. Tier 3 — independent validation

### SEN2NEON

This is the key.

Use it as:

> **12-band 2.5 m real-reference validation.**

Do not train on it if we're using it as our primary independent benchmark.

---

# 27. Tier 4 — independent cross-sensor validation

### OpenSR-Test

Use:

* NAIP
* SPOT
* Venµs
* Spain Crops
* Spain Urban.

This tells us whether performance is dependent on one HR sensor/reference environment. ([GitHub][8])

---

# 28. Tier 5 — Indian domain evaluation

This is where FRAME can potentially become distinctive.

Acquire:

```text
Indian Sentinel-2 L2A
```

through:

* Bhoonidhi
* Copernicus.

Then seek appropriate Indian HR references where legally/data-access feasible.

Potential candidates:

* Cartosat
* Resourcesat
* aerial datasets
* public Indian orthophotos where available
* other co-registered HR satellite data.

But we need to be very careful here.

### Do not build the claim:

> "India has no HR data."

It does.

### Instead:

> "We evaluate model transfer on Indian Sentinel-2 scenes, with HR reference validation where accessible."

---

# 29. Should we create our own Indian paired dataset?

Potentially.

But **not yet as a first priority**.

Creating a scientifically valid Indian LR-HR dataset requires:

### Temporal matching

The images need to be close in time.

### Spatial registration

Pixel-level alignment.

### Spectral harmonisation

Different sensors see different spectral responses.

### PSF differences

Different sensors blur spatial information differently.

### Atmospheric differences

Different acquisition conditions.

### Licensing

We must have the right to redistribute/use the reference data.

### Quality control

Bad pairs can damage the model.

Therefore:

> **Do not create an Indian dataset just for the PPT.**

If we create one, it should follow the same scientific standards as SEN2NAIP/SEN2NEON.

---

# 30. Synthetic degradation — should FRAME create its own?

Initially:

**No.**

We should first reproduce/understand the established SEN2NAIPv2 degradation.

Why?

Because building a new degradation model before establishing a baseline would make it impossible to tell whether our SR improvements come from:

* architecture
* degradation model
* dataset
* training protocol.

---

# 31. But later we may need a FRAME-specific degradation model

This is a legitimate research possibility.

If we eventually identify:

> SEN2NAIPv2's degradation assumptions don't represent Indian Sentinel-2 observations well,

then we can investigate:

```text
Indian real LR-HR pairs
        ↓
learn Indian-specific degradation
        ↓
synthetic Indian S2-like dataset
        ↓
SR training
```

That could become a much stronger research contribution.

But it requires evidence first.

---

# 32. Dataset splitting is critical

This is a major point that often gets overlooked.

Do **not** randomly split patches.

Suppose one 100 km² region contains:

```text
100,000 patches
```

and we randomly do:

```text
80% train
20% test
```

The model may see almost the same geography in both sets.

That produces spatial leakage.

CloudSEN12's methodology explicitly uses spatially stratified block splitting to avoid this problem. ([Nature][11])

FRAME should adopt the same principle.

---

# 33. Recommended split strategy

For our own training dataset:

```text
GEOGRAPHIC REGION
        ↓
whole-region split
        ↓
TRAIN
VALIDATION
TEST
```

Never:

```text
random patches
↓
train/test
```

unless the purpose is explicitly an interpolation test.

---

# 34. Even better: geographic holdout

For our eventual Indian experiment:

```text
Tamil Nadu
→ Test

Other training geography
→ Train

Another Indian region
→ Validation
```

This answers:

> Does the model generalize to a genuinely unseen geography?

That's much stronger.

---

# 35. What should be TRAIN vs VALIDATION vs TEST?

My current recommendation:

## TRAIN

### Primary

**SEN2NAIPv2 synthetic**

### Supplementary

**SEN2VENµS**

Potentially carefully selected synthetic data derived from public HR imagery.

---

## VALIDATION

### SEN2NAIPv2 cross-sensor

Useful during development because it is closely tied to the training ecosystem.

But don't rely on it alone.

---

## FINAL TEST

### SEN2NEON

12-band / 2.5m.

### OpenSR-Test

NAIP + SPOT + Venµs + Spain.

### Indian holdout

Our own Indian test scenes.

This is a strong three-layer test.

---

# 37. What is the strongest possible FRAME training strategy?

I currently see two realistic paths.

## Path A — reproduce state of the art first

```text
SEN2NAIPv2
      ↓
reproduce SEN2SR-style training
      ↓
validate
      ↓
establish baseline
      ↓
modify FRAME
```

### Advantage

Scientifically clean.

We know what the baseline is.

---

## Path B — train directly on a custom 12-band dataset

```text
custom 12-band dataset
↓
FRAME
```

### Problem

Huge dataset-generation burden.

And we'd potentially reinvent SEN2NAIP/SEN2NEON methodology.

### Verdict

**Do not start here.**

---

# 38. Recommended approach

### Phase 1

Reproduce an established SEN2SR-type baseline using its public training/data methodology.

### Phase 2

Evaluate it on:

* SEN2NEON
* OpenSR-Test.

### Phase 3

Add FRAME-specific components.

For example:

```text
baseline SR
      ↓
stability layer
      ↓
downstream evaluation
```

### Phase 4

Indian-domain evaluation.

This gives us a scientifically clean comparison.

---

# 39. This also changes how we should describe FRAME's "own model"

Our PPT currently says:

> "Our own model trained on all 12 bands."

That's potentially problematic.

Because:

1. Existing models already process multispectral bands.
2. SEN2NEON already benchmarks all 12.
3. SEN2SR is already a mature current system.

Instead, we should eventually say something like:

> **FRAME evaluates and extends current Sentinel-2 SR approaches within an analysis-oriented pipeline, with explicit stability evidence and downstream geospatial validation.**

If we genuinely develop a new architecture, then we can later specify:

> "FRAME-SR: our modified architecture..."

But **we shouldn't invent an architecture just to claim ownership.**

# 41. What remains technically difficult?

### 1. Realistic degradation

Getting synthetic LR to behave like actual Sentinel-2.

### 2. Spectral cross-sensor harmonisation

Especially for different HR sensors.

### 3. Geographic diversity

Most strong public datasets are not Indian.

### 4. 12-band 2.5m training

Public data are much more limited than RGBN.

### 5. Downstream relevance

Does training on one benchmark produce useful information elsewhere?

### 6. Domain shift

Does the model hallucinate or lose fidelity in unfamiliar landscapes?

### 7. Benchmark contamination

Avoiding leakage between train and evaluation regions.

The dataset itself:

**No.**

But a potential contribution is:

> **A geographically held-out evaluation strategy that combines public 12-band 2.5 m validation with Indian-domain testing to determine whether Sentinel-2 SR reconstruction quality and model stability transfer across regions.**

That is much stronger.

Potentially:

> **A domain-aware degradation strategy adapted to Indian Sentinel-2 observations, if real Indian LR-HR evidence demonstrates that existing degradation models do not transfer adequately.**

This is **conditional**.

```text

        ↓
Indian test
        ↓
performance degradation
        ↓
evidence that degradation mismatch is causal
```

Only then should we build an Indian-specific degradation model.

The most important conclusion is:

> **We do not need to invent FRAME's own global LR-HR dataset. The ecosystem has matured enough that our job should be to use the right dataset for the right purpose.**

# SIH26142 — FRAME

## REQUIREMENT 4 — SUPER-RESOLUTION MODEL

This is the most important technical requirement so far.

The question is no longer:

> "What deep-learning model can make Sentinel-2 sharper?"

That problem is already heavily solved.

The real question is:

> **Which SR architecture should FRAME use, given that the current state of the art already reaches 2.5 m, supports multispectral Sentinel-2 data, explicitly addresses spectral/spatial consistency, and in some cases even provides pixel-level uncertainty?**

After the current research, I would **not recommend inventing a completely new SR architecture at the beginning**.

We should establish a strong modern baseline first, then only modify it if our experiments identify a real deficiency.

---

# 1. NTRO requirement

The PS asks for:

> Deep-learning-based super-resolution from medium-resolution Sentinel-2 imagery to a product below 4 m, while preserving spectral and geospatial consistency.

For FRAME, that translates to:

```text
Input:
Sentinel-2 L2A

Target:
reconstructed 2.5 m grid

Scale:
4× relative to 10 m

Spectral:
multispectral

Constraints:
spectral consistency
spatial consistency
low hallucination
geospatial alignment
```

And because our project has moved toward evidence-aware analysis:

```text
SR output
+
stability/reliability evidence
```

should ultimately accompany the reconstructed image.

---

# 2. The architecture landscape

The relevant architecture families are:

1. CNN / residual CNN
2. GAN
3. Transformer
4. Mamba/state-space models
5. Latent diffusion
6. Hybrid architectures

All of them have been applied to remote-sensing SR.

But they have very different trade-offs.

---

# 3. CNN / residual networks

CNNs remain extremely important because SR is fundamentally a local spatial reconstruction problem.

Classic SR architectures include:

* SRCNN
* EDSR
* RDN
* RCAN
* ResNet-style networks.

For Sentinel-2 specifically, residual CNNs have already been used to generate **2.5 m** products by combining Sentinel-2 with PlanetScope imagery. A 2020 study used 10 Sentinel-2 bands and residual CNNs for 2.5 m fusion. ([mdpi.com](https://www.mdpi.com/2072-4292/12/15/2366?utm_source=chatgpt.com))

### Advantages

* mature
* relatively efficient
* stable
* easier to train
* easier to deploy
* lower compute than diffusion
* easier to reproduce

### Weakness

CNN receptive fields are comparatively local unless heavily engineered.

For large contextual structures:

> Transformer/Mamba approaches can potentially model longer-range relationships more efficiently.

---

# 4. GANs

GAN-based SR became popular because they produce visually sharp results.

Examples include:

* SRGAN
* ESRGAN
* MTSR-GAN.

A 2025 MTSR-GAN specifically targets:

> Sentinel-2 10 m → 2.5 m

and combines a Mamba-derived module with Transformer cross-attention. ([tandfonline.com](https://www.tandfonline.com/doi/full/10.1080/01431161.2025.2518505?utm_source=chatgpt.com))

### Why GANs are attractive

They can generate:

* sharp edges
* high-frequency textures
* visually convincing detail.

### But this is exactly the danger for FRAME.

A GAN can generate plausible details that weren't actually observed.

For example:

```text
road
↓
model sees texture
↓
generates vehicle-like structure
```

even though the original Sentinel-2 measurement doesn't support it.

That is effectively hallucination.

Therefore:

> **GAN perceptual sharpness cannot be our primary optimization objective.**

---

# 5. Transformer-based SR

Transformers introduced long-range attention into SR.

A 2025 IEEE paper proposed a Transformer-based Sentinel-2 SR architecture using:

* multi-head attention
* spatial attention
* channel attention

and reported improved PSNR/SSIM over several benchmark architectures on its experimental setup. ([ieeexplore.ieee.org](https://ieeexplore.ieee.org/document/10829708/?utm_source=chatgpt.com))

Transformers are attractive because they can model relationships between distant spatial regions.

### Strengths

* global context
* strong representation capacity
* good performance
* useful for complex spatial structure.

### Weaknesses

Standard self-attention can become computationally expensive for large images.

Swin-style windowed attention addresses some of this.

---

# 6. Swin Transformer

Swin Transformer introduced hierarchical/windowed attention.

This makes Transformer-style SR much more computationally manageable.

SEN2SR explicitly evaluates **Swin Transformer** alongside CNN and Mamba approaches. ([doi.org](https://doi.org/10.1016/j.rse.2025.115222?utm_source=chatgpt.com))

Therefore:

> Swin is absolutely a valid FRAME baseline.

But there is no reason to choose it automatically over the current SEN2SR Mamba approach.

---

# 7. Mamba / State Space Models

This is currently one of the most interesting architectures for FRAME.

SEN2SR's full model uses **Mamba**.

The official implementation describes the full SEN2SR version as using Mamba and requiring GPU/CUDA support. ([github.com](https://github.com/ESAOpenSR/SEN2SR?utm_source=chatgpt.com))

Mamba/state-space architectures are attractive because they can model long-range dependencies with a more favourable scaling behaviour than full attention.

Conceptually:

```text
CNN:
local spatial relationships

Transformer:
global relationships through attention

Mamba:
long-range sequence/state modelling
with more efficient scaling
```

This makes Mamba especially interesting for:

* large remote-sensing images
* long spatial dependencies
* large receptive fields
* efficient contextual modelling.

---

# 8. SEN2SR's model family

The current ESA OpenSR ecosystem is particularly useful because it provides several variants rather than one black-box model.

The repository currently exposes:

### SENSRLite

Lightweight model.

### SENSR

More accurate lightweight model.

### LDSR-S2

Latent diffusion model.

### SEN2SR

Full model using Mamba. ([github.com](https://github.com/ESAOpenSR/SEN2SR?utm_source=chatgpt.com))

This is excellent for our benchmarking because we can compare:

```text
CNN
vs
Mamba
vs
Diffusion
```

without implementing all three architectures from scratch.

---

# 9. Current SEN2SR pipeline is actually multi-stage

This is important.

The current released model ecosystem isn't simply:

```text
12 × 10m
↓
Mamba
↓
12 × 2.5m
```

The public model variants include a multi-stage structure.

The current model documentation describes:

### Stage 1

10 m RGBN:

```text
B2 B3 B4 B8
↓
4×
↓
2.5m
```

### Stage 2

20 m bands:

```text
B5 B6 B7 B8A B11 B12
↓
2×
↓
10m
```

followed by:

```text
10m
↓
4×
↓
2.5m
```

The full 10-band pipeline therefore combines the RGBN 4× stage with the 20 m band sharpening stage. ([huggingface.co](https://huggingface.co/WEO-SAS/sen2sr/blob/main/README.md?utm_source=chatgpt.com))

This is extremely relevant to the FRAME architecture we were previously discussing.

---

# 10. SEN2SR currently has a major limitation for our original plan

The current full public pipeline focuses on **10 Sentinel-2 bands**:

```text
B2 B3 B4 B8
B5 B6 B7 B8A B11 B12
```

It does not include:

```text
B1
B9
```

in the full 10-band 2.5 m pipeline. ([huggingface.co](https://huggingface.co/WEO-SAS/sen2sr/blob/main/README.md?utm_source=chatgpt.com))

That is because B1 and B9 originate at 60 m.

Therefore our original statement:

> "FRAME uses 12 bands at 2.5 m"

needs another qualification.

It is technically possible to construct a 12-channel 2.5 m output grid.

But:

> **Current state-of-the-art public SEN2SR does not establish that B1/B9 should be learned to 2.5 m in the same manner as the 10 m/20 m bands.**

This is an important open design question.

---

# 11. This is where FRAME has an actual technical experiment

We now have:

### Configuration A

```text
10 bands
B2 B3 B4 B5 B6 B7 B8 B8A B11 B12
```

### Configuration B

```text
12 bands
+
B1/B9
```

We should test whether B1/B9 actually provide useful information at 2.5 m.

This is much more scientifically meaningful than saying:

> "12 bands is our novelty."

---

# 12. Latent diffusion

The other major modern architecture is diffusion.

The **LDSR-S2** paper is especially important because it explicitly targets trustworthy Sentinel-2 SR.

The model:

* uses latent diffusion rather than full image-space diffusion
* conditions on the LR Sentinel-2 input
* super-resolves 10 m → 2.5 m
* uses visible + NIR bands
* generates pixel-level uncertainty information. ([ieeexplore.ieee.org](https://ieeexplore.ieee.org/document/10887321/?utm_source=chatgpt.com))

This is extremely relevant to FRAME.

---

# 13. Why diffusion is interesting

Diffusion models can represent a distribution of plausible HR outputs rather than producing only one deterministic reconstruction.

Conceptually:

```text id="3q1q5y"
LR observation
      ↓
conditional diffusion
      ↓
sample 1
sample 2
sample 3
...
sample N
      ↓
distribution
      ↓
mean / uncertainty
```

This gives us something CNN/Mamba deterministic models don't naturally provide:

> **output variability as an uncertainty signal.**

---

# 14. LDSR-S2 uncertainty is actually stronger than our original TTA idea

This is an important correction.

We previously proposed:

> six geometric TTA views → output variance → uncertainty.

But LDSR-S2 already provides a much more principled mechanism.

The OpenSR project describes running the diffusion model multiple times for the same LR input and calculating pixel-wise variation.

The width of the resulting confidence interval increases where the model has greater uncertainty, particularly in high-texture regions. ([cin.philab.esa.int](https://cin.philab.esa.int/databases/projects/towards-explainable-ai-application-to-trustworthy-super-resolution-opensr-robust-accountable-super-resolution-for-sentinel-2?utm_source=chatgpt.com))

This is significantly closer to genuine **predictive uncertainty** than TTA variance.

---

# 15. But diffusion has a serious cost

The same OpenSR project reports that generating multiple samples can increase computational cost by roughly **10–20×**. ([cin.philab.esa.int](https://cin.philab.esa.int/databases/projects/towards-explainable-ai-application-to-trustworthy-super-resolution-opensr-robust-accountable-super-resolution-for-sentinel-2?utm_source=chatgpt.com))

That's huge.

FRAME has:

* student/hackathon compute constraints
* potentially large images
* potentially many scenes
* an operational API/web viewer.

Therefore:

> **Diffusion is scientifically attractive but operationally expensive.**

---

# 16. Current benchmark evidence is revealing

SEN2NEON's current benchmark reports:

| Model        |      PSNR |     SSIM |  SAM | Spectral consistency | Spatial consistency |
| ------------ | --------: | -------: | ---: | -------------------: | ------------------: |
| S2SR-LDSR-S2 |     31.98 |     0.78 | 0.05 |                 2.20 |               0.019 |
| S2SR-Lite    | **32.56** |     0.80 | 0.04 |                 1.52 |               0.004 |
| S2SR-Mamba   |     32.44 | **0.81** | 0.05 |                 2.20 |           **0.006** |
| SRGAN        |     31.40 |     0.73 | 0.05 |             **1.21** |               0.020 |

These are benchmark means and should not be interpreted as a universal ranking across all datasets. But they demonstrate the central issue: **there is no single architecture that dominates every quality dimension.** ([github.com](https://github.com/ESAOpenSR/SEN2NEON?utm_source=chatgpt.com))

That is very important for FRAME.

---

# 17. What this means for model selection

We should not say:

> "Mamba is the best."

or:

> "Diffusion is the best."

The evidence says the trade-off depends on what we optimize.

For FRAME:

### Priority 1

Spectral correctness.

### Priority 2

Spatial correctness.

### Priority 3

Low hallucination.

### Priority 4

Downstream analytical utility.

### Priority 5

Computational feasibility.

### Priority 6

Model-stability/reliability evidence.

That is a different objective from:

> maximum perceptual sharpness.

# 33. Loss function

We should not simply use MSE.

A likely baseline objective:

```text id="zpsf3a"
L = λ1 L_pixel
  + λ2 L_spectral
  + λ3 L_perceptual
  + λ4 L_consistency
```

But we need to be careful with perceptual loss.

For natural images:

> perceptual sharpness is desirable.

For Earth observation:

> perceptual hallucination can be dangerous.

Therefore the loss should prioritize physical/spectral fidelity.

# 34. SEN2SR's low-frequency hard constraint

This is one of the most important ideas we should borrow.

The current SEN2SR framework explicitly enforces the original low-frequency information after SR.

Conceptually:

```text id="0j8y6a"
Input
 │
 ├── bilinear upsample
 │       ↓
 │   low-frequency component
 │
 └── SR network
         ↓
    high-frequency component

low-frequency input
+
generated high-frequency detail
↓
final SR
```

This ensures that the network isn't free to modify the original large-scale spectral structure.

The paper describes the frequency-domain hard-constraint layer using low-pass/high-pass filtering and Fourier transforms. ([sciencedirect.com](https://www.sciencedirect.com/science/article/pii/S0034425725006261?utm_source=chatgpt.com))

### Recommendation:

**FRAME should adopt this principle rather than invent another spectral-preservation mechanism.**

# SIH26142 — FRAME

## REQUIREMENT 5 — SPECTRAL CONSISTENCY

This requirement needs a very strict distinction:

> **Spectral consistency is not FRAME's novelty.**

It is already an explicit objective of modern Sentinel-2 SR systems, especially SEN2SR, which introduces a low-frequency hard constraint specifically to preserve the original spectral content. ([ScienceDirect][1])

Our job is therefore to determine **how FRAME should preserve, measure, and prove spectral consistency**, and whether we can connect that evidence to downstream analytical reliability.

---

# 1. What NTRO requires

The PS specifically requires the SR product to preserve:

> **spectral consistency**

This means the reconstructed 2.5 m pixels must not arbitrarily change the physical spectral behaviour observed by Sentinel-2.

That matters because Sentinel-2 isn't merely an RGB photograph.

Its bands are measurements used to derive:

* vegetation indices
* water indices
* built-up indices
* vegetation properties
* crop characteristics
* burn severity
* material information
* land-cover classes.

If SR creates visually convincing but spectrally incorrect pixels, the output can become **less useful scientifically despite looking sharper**.

SEN2NAIP makes this point explicitly: remote-sensing pixel values carry information relevant to physical/environmental interpretation, so spectral coherence matters independently of visual sharpness. ([Nature][2])

---

# 2. What "spectral consistency" actually means

There are several different levels.

## Level 1 — Global radiometric consistency

The average/overall reflectance shouldn't shift dramatically.

Example:

```text id="9tq3cz"
Original 10m B4:
mean = 0.21

SR → downsampled:
mean = 0.211
```

Good.

But this alone is insufficient.

---

## Level 2 — Band-wise consistency

Each spectral band should maintain its relationship with the original observation.

For example:

```text id="r1qg7j"
B4
B8
```

should preserve the physical relationship needed for NDVI.

---

## Level 3 — Spectral-vector consistency

For every location, the reconstructed spectrum:

```text id="l9m6de"
[B1, B2, B3, ... B12]
```

should remain close in spectral shape to the reference/expected spectrum.

This is where **Spectral Angle Mapper (SAM)** becomes important.

---

## Level 4 — Index consistency

Derived indices should not change arbitrarily.

For example:

```text id="4e5o1r"
NDVI_original
        vs
NDVI_SR_downsampled
```

Likewise:

* NDWI
* NDBI
* BSI
* MNDWI.

SEN2SR explicitly investigates downstream spectral indices and reports that indices such as MNDWI and MBMP remain stable after SR. ([DOI][3])

---

# 3. The most important test: downsample back to the observation resolution

This should become a core FRAME test.

Suppose:

```text id="c6q4qz"
Original:
10m Sentinel-2

        ↓
FRAME

2.5m reconstructed image

        ↓
Downsample 4×
using the defined observation operator

10m reconstructed equivalent
```

Then compare:

```text id="f8f3fs"
Original Sentinel-2
vs
downsampled FRAME
```

This asks:

> **Did FRAME introduce spectral changes that are inconsistent with the original observation?**

This is much more meaningful than simply comparing the 2.5 m image visually.

---

# 4. This is already part of SEN2SR

SEN2SR specifically introduces a **low-frequency hard constraint** at the end of the network.

The objective is essentially:

```text id="z6e9l1"
Original LR observation
        │
        ├───────────────┐
        │               │
        ▼               ▼
 low-frequency      SR network
 component           output
        │               │
        └───────┬───────┘
                ▼
       constrained SR
```

The paper describes this as enforcing spectral consistency by preserving the original low-frequency content. ([ScienceDirect][1])

This is important because we **shouldn't reinvent it**.

---

# 5. What the low-frequency constraint is trying to prevent

Imagine the model predicts:

```text id="1s3f7v"
Original large-scale structure
       ↓
SR model
       ↓
dramatically different reflectance
```

That would mean the model isn't simply adding fine detail.

It is changing the underlying observation.

Instead:

```text id="v5g0y4"
Original low-frequency information
            +
learned high-frequency information
            ↓
SR output
```

is a more physically constrained formulation.

---

# 6. This gives FRAME a critical principle

Our architecture should conceptually follow:

> **SR should primarily reconstruct spatial detail while preserving the information already supported by the original observation.**

That is much stronger than:

> "make the image sharper."

---

## DSen2

Therefore:

**Spectral preservation is not new.**

---

Again:

**Not new.**

This is particularly important because:

> **Even before the SR model runs, LR-HR pair construction can introduce spectral mismatch.**

Therefore spectral consistency is partly a **dataset problem**, not merely a model-loss problem.

This is currently the strongest reference for FRAME. ([ScienceDirect][1])

The important observation isn't which model "wins."

It is:

> **Different architectures trade off spectral, spatial and perceptual properties.**

Therefore we cannot optimize one metric in isolation.

# 10. Why PSNR alone is inadequate

Suppose Model A:

```text
PSNR = 33
```

and Model B:

```text
PSNR = 32
```

Model A isn't automatically better for remote sensing.

Suppose A also:

```text
SAM = worse
NDVI consistency = worse
spectral consistency = worse
```

Then A may produce a numerically better reconstruction while being less useful for spectral analysis.

This is precisely why recent Sentinel-2 SR evaluation uses multiple spectral and thematic metrics rather than PSNR alone. ([MDPI][5])

---

# 11. Required FRAME metric stack

I recommend dividing the metrics into four groups.

## A. Pixel reconstruction

### RMSE

Measures absolute reconstruction error.

### MAE

More robust to outliers than RMSE.

### PSNR

Standard image reconstruction metric.

### SSIM

Structural similarity.

---

# 12. B. Spectral metrics

## SAM — Spectral Angle Mapper

For each pixel:

```text id="g7x5dn"
SR spectral vector
        vs
reference spectral vector
```

calculate the angle.

Smaller:

> more spectrally similar.

This is one of the most important metrics for FRAME.

SEN2NAIP itself uses spectral angle distance for cross-sensor quality control. ([Nature][2])

---

# 13. ERGAS

ERGAS provides a relative global reconstruction error across bands.

This is particularly useful for multispectral imagery because it considers band-wise normalized error rather than only raw pixel differences.

Therefore:

> **FRAME should include ERGAS.**

---

# 14. Spectral correlation

Calculate correlation between:

```text id="5abq8n"
Original band
vs
SR-downsampled band
```

for each band.

This helps detect cases where:

* overall brightness is similar
* but spatial/spectral relationships have changed.

---

# 15. Reflectance bias

Calculate:

```text id="9n3gsg"
mean(SR_downsampled - original)
```

per band.

Also:

```text
MAE
RMSE
PBIAS
```

SEN2NAIP uses PBIAS, MAE and RMSE alongside spectral angle to evaluate whether its synthetic degradation accurately reproduces Sentinel-2 reflectance. ([Nature][2])

---

# 16. C. Derived-index consistency

This is where FRAME can move beyond conventional SR evaluation.

For each index:

```text id="n6m2kc"
NDVI
NDWI
NDBI
BSI
MNDWI
```

compare:

```text
index(original S2)
vs
index(SR → observation grid)
```

Calculate:

* MAE
* RMSE
* correlation
* bias
* distribution difference.

---

# 17. Why this matters

Imagine:

```text id="v1g7op"
Spectral metrics:
excellent

but

NDVI:
large deviation
```

Then something is wrong.

Or:

```text
PSNR:
excellent

NDVI:
stable
NDBI:
stable
NDWI:
stable
```

Then the reconstruction has much stronger evidence of analytical usefulness.

This is the direction I want FRAME to emphasize.

---

# 18. D. Spatial-spectral consistency

OpenSR-Test adds another important concept.

It evaluates:

### Reflectance consistency

Does the output remain consistent with the LR observation?

### Spectral consistency

Does the spectrum remain correct?

### Spatial consistency

Does the generated spatial structure behave appropriately?

### Synthesis

How much new high-frequency information did the model generate?

But there is a critical caveat:

> **A high synthesis score does not prove that generated detail is real.**

The recent geospatial information-extraction study explicitly states that synthesis measures the amount of introduced high-frequency information but does not itself establish whether that information is realistic or an artifact. ([MDPI][5])

That is extremely important for FRAME.

---

# 19. FRAME should therefore separate:

```text id="8z7p3a"
NEW DETAIL
      ≠
REAL DETAIL
      ≠
USEFUL DETAIL
```

This is one of the strongest conceptual ideas in the project.

A model can:

### Generate detail

Yes.

### Generate realistic detail

Maybe.

### Generate analytically useful detail

Maybe.

Those are three different questions.

# 22. Critical question: how exactly should we downsample?

This matters.

If we generate:

```text
2.5m → 10m
```

using a completely arbitrary interpolation method, our validation itself becomes questionable.

The downsampling operator should reflect the observation process as closely as possible.

SEN2SR explicitly formulates the relationship between LR and HR using a degradation/observation process rather than simply assuming arbitrary image resizing. ([ScienceDirect][1])

Therefore:

> FRAME should define and document its observation-grid reduction operator.

This becomes part of the experimental protocol.

# 23. Recommended validation operator

For initial reproducibility:

### Primary

Area-appropriate aggregation/downsampling consistent with the sensor grid.

### Secondary

Bicubic comparison.

### Sensitivity experiment

Compare the results under different reduction operators.

Why?

Because if our conclusion changes dramatically depending on whether we use:

* average
* bicubic
* Gaussian + decimation

then our spectral-consistency conclusion isn't robust.

---

# 24. Hard constraint vs loss

There are two ways to enforce spectral consistency.

## Method A — loss

Add:

```text id="3a8ezr"
L_spectral
```

to the training objective.

For example:

```text
L_total =
λ1 L_reconstruction
+
λ2 L_SAM
+
λ3 L_spectral
```

### Advantage

Flexible.

### Weakness

The model can still violate the constraint.

---

# 25. Method B — architectural hard constraint

SEN2SR's approach is stronger.

The final output is constrained so that the low-frequency content is consistent with the original observation.

Conceptually:

```text id="6lkwr9"
SR_prediction
+
original low-frequency information
→
constrained output
```

### Advantage

The model cannot arbitrarily modify that component.

### Recommendation

**Use the SEN2SR low-frequency constraint as our primary reference rather than inventing a new one.**

This remains an important FRAME guardrail.

# SIH26142 — FRAME

## REQUIREMENT 6 — GEOSPATIAL CONSISTENCY

This requirement is more important than it initially appears.

For FRAME, **spectral correctness is not enough**.

A reconstructed object can have the right spectral signature but be:

* shifted by a few pixels,
* spatially distorted,
* misregistered between bands,
* inconsistent with the original Sentinel-2 grid,
* incorrectly positioned relative to roads/buildings/field boundaries.

That becomes a serious problem once we start doing:

* land-cover mapping,
* area calculation,
* change detection,
* urban growth mapping,
* flood extent mapping,
* crop-boundary analysis.

And importantly, **current SOTA already recognizes this problem**. SEN2SR explicitly targets spatial alignment/geometric consistency, so this cannot be claimed as FRAME's invention. ([DOI][1])

---

# 1. Exact NTRO interpretation

The requirement is essentially:

> Generate a higher-resolution product while maintaining the correct geographic/spatial relationship of the original Sentinel-2 observation.

For FRAME, this means the output must preserve:

1. CRS
2. affine transform
3. image bounds
4. pixel orientation
5. geographic extent
6. alignment between bands
7. alignment with the original Sentinel-2 observation
8. alignment with HR reference data during validation
9. spatial relationships of reconstructed features.

The most important principle:

> **2.5 m output means a reconstructed 2.5 m grid, not that Sentinel-2 actually observed 2.5 m detail.**

---

# 2. Why spatial consistency is different from spatial sharpness

These are often confused.

Consider:

```text
Original Sentinel-2

████████████████
████████████████
████████████████


SR Output

  ████████████████
  ████████████████
```

The SR image might look extremely sharp.

But if everything has shifted:

```text
Original building:
      █████

SR building:
         █████
```

then the reconstruction is geographically wrong.

Therefore:

> **Sharper ≠ spatially correct.**

The recent SEN2SR paper explicitly identifies geometric misalignment and nonexistent local structures as problems in existing SR systems. ([DOI][1])

---

# 3. What exactly needs to remain aligned?

## A. Pixel grid

Suppose original:

```text
10 m pixel grid
```

FRAME:

```text
2.5 m grid
```

Every 4×4 group of 2.5 m pixels must correspond to the appropriate original 10 m footprint under the defined observation/degradation model.

---

## B. Image extent

If the original covers:

```text
xmin = X1
xmax = X2
ymin = Y1
ymax = Y2
```

the SR product must represent the same geographic area.

---

## C. CRS

For example:

```text
EPSG:32644
```

must not silently become something else.

---

## D. Affine transform

The GeoTIFF needs the correct:

```text
transform
```

describing:

* pixel size
* origin
* orientation
* spatial relationship.

---

## E. Inter-band registration

This is especially important for FRAME because we're using multiple Sentinel-2 bands.

For example:

```text
B4 → red
B8 → NIR
B11 → SWIR
```

If their reconstructed features are spatially displaced relative to each other:

```text
B4 building edge
       ↓
       ████

B8 building edge
          ↓
          ████
```

then:

```text
NDVI
NDBI
NDWI
```

can become spatially corrupted.

---

# 4. Native Sentinel-2 grids complicate this

Sentinel-2 does **not** provide every band at the same native resolution.

We have:

| Native resolution                                   | Bands                     |
| --------------------------------------------------- | ------------------------- |
| 10 m                                                | B2, B3, B4, B8            |
| 20 m                                                | B5, B6, B7, B8A, B11, B12 |
| 60 m                                                | B1, B9                    |
| 60 m acquisition band but excluded from standard SR | B10                       |

Therefore, before SR:

```text
10m bands
20m bands
60m bands
```

have different native sampling grids.

FRAME eventually wants:

```text
2.5m common reconstructed grid
```

That makes spatial harmonisation critical.

---

# 5. Existing solution — ordinary geospatial resampling

The simplest solution is:

```text
reproject/resample
       ↓
common grid
```

using tools such as:

* GDAL
* Rasterio
* Warp/reproject
* bilinear
* cubic
* nearest neighbour.

This solves the **engineering problem of putting data onto a common grid**.

It does not solve the SR problem.

Therefore:

> Common-grid resampling is necessary but not a novelty.

---

# 6. Existing solution — SEN2SR

This is currently the most important reference.

SEN2SR explicitly targets:

> spectral and spatial alignment consistency.

Its training pipeline harmonizes synthetic training data to Sentinel-2's spectral and spatial characteristics.

It also evaluates spatial consistency and geometric alignment. ([DOI][1])

Therefore FRAME should **build on this methodology**, not pretend spatial consistency is unsolved.

---

# 7. Existing solution — OpenSR-Test

This is particularly useful for us.

OpenSR-Test explicitly separates:

* reflectance consistency
* spectral consistency
* spatial consistency
* synthesis
* hallucination
* omission
* improvement.

Its datasets are specifically constructed to minimize spatial and spectral misalignment. ([GitHub][2])

This means FRAME can use an established evaluation ecosystem instead of inventing arbitrary spatial metrics.

---

# 8. How OpenSR-Test evaluates spatial alignment

SEN2NAIP gives an excellent example.

During S2–NAIP pair construction, they identify matching control points using feature-matching algorithms including:

* LightGlue
* DISK

and calculate spatial quality from the mean absolute error of the matched ground-control points.

Pairs with spatial error greater than one pixel were discarded. ([Nature][3])

This is extremely useful for FRAME.

It establishes that:

> **Spatial alignment can and should be quantitatively checked before treating an HR reference as ground truth.**

---

# 9. Indian solution

India already has extensive geospatial infrastructure:

* ISRO/NRSC EO data
* Bhoonidhi
* standard CRS/georeferencing
* GIS processing
* Cartographic/remote-sensing workflows.

But the relevant point for FRAME is:

**The underlying geospatial infrastructure is mature.**

The research gap isn't:

> "India doesn't know how to georeference satellite imagery."

It is:

> **How reliably does a learned SR model preserve geospatial alignment while inventing sub-pixel spatial detail?**

That's a much more legitimate research question.

---

# 10. Industry solution

Commercial GIS/EO systems generally solve:

### Geometric processing

Using:

* orthorectification
* reprojection
* resampling
* sensor models
* ground control
* image registration.

Commercial remote-sensing software therefore already has mature solutions for geographic alignment.

Again:

> FRAME does not need to invent GIS georeferencing.

The challenge is **SR-induced spatial distortion**.

---

# 11. The actual SR-specific problem

Consider a 10 m Sentinel-2 pixel:

```text
+--------------------+
|                    |
|      building      |
|                    |
+--------------------+
```

The SR model generates:

```text
+--+--+--+--+
|  |  |  |  |
+--+--+--+--+
|  |██|██|  |
+--+--+--+--+
|  |██|██|  |
+--+--+--+--+
|  |  |  |  |
+--+--+--+--+
```

Those 2.5 m boundaries are **model-generated**.

They are not directly observed by Sentinel-2.

Therefore we need to ask:

> Does the generated boundary align with independent HR evidence?

That's the central geospatial-consistency question.

---

# 12. What does "spatial consistency" mean mathematically?

At minimum:

```text
Original observation
       ↓
SR
       ↓
degradation / aggregation
       ↓
SR-observation equivalent
```

should preserve spatial structures compatible with the original observation.

At HR validation:

```text
SR
vs
HR reference
```

we can measure:

* spatial distance
* edge alignment
* feature displacement
* structural similarity
* hallucination
* omission.

---

# 13. Important OpenSR concept: hallucination vs omission

This is extremely relevant to FRAME.

Suppose the HR reference contains:

```text
road
```

but SR doesn't reproduce it.

That's an:

> **omission**

Suppose SR generates:

```text
road
```

where the HR reference doesn't contain one.

That's:

> **hallucination**

Suppose SR reconstructs the feature correctly:

> improvement/correct synthesis.

OpenSR-Test explicitly provides these kinds of normalized distances. ([GitHub][2])

This gives FRAME a much better vocabulary than simply saying:

> "The image looks sharper."

---

# 14. Current benchmark evidence

OpenSR-Test's current benchmark shows very different spatial-consistency behaviour between models.

For example, in its current reported results:

| Model        | Spatial consistency ↓ | Synthesis ↑ |
| ------------ | --------------------: | ----------: |
| OpenSR model |                0.0118 |      0.0194 |
| SuperImage   |                0.0004 |      0.0130 |
| Satlas       |                0.2766 |      0.0648 |
| SR4RS        |                1.0099 |      0.0509 |

These numbers demonstrate something important:

> Models that generate more high-frequency information do not necessarily have better spatial consistency. ([GitHub][2])

This is exactly why FRAME needs separate spatial and synthesis evaluation.

SEN2NEON provides:

* co-registered AVIRIS-NG-derived reference
* 12 Sentinel-2-equivalent bands
* spatially aligned tiles.

The canonical benchmark uses 2.5 m HR tiles aligned to the 10 m LR grid. ([GitHub][4])

This is nearly ideal for FRAME's final validation.

rather than merely:

# SIH26142 — FRAME

## REQUIREMENT 7 — FINE-SCALE DETAIL / SPATIAL INFORMATION RECONSTRUCTION

This is where the project reaches the **actual scientific core**.

Requirements 1–6 mostly established that:

* Sentinel-2 can be acquired reliably.
* Its bands can be harmonized.
* LR-HR training data exists.
* SOTA SR models already exist.
* Spectral consistency is already researched.
* Geospatial consistency is already researched.

Requirement 7 asks the harder question:

> **What does FRAME actually mean by "fine-scale detail", and how do we prove that the detail generated at 2.5 m is useful rather than merely plausible-looking?**

This distinction is critical because current Sentinel-2 SR research explicitly separates **consistency, synthesis, and correctness**. SEN2SR describes three possibilities for newly generated high-frequency information: **improvement, omission, or hallucination**. ([DOI][1])

---

# 1. Exact NTRO interpretation

The PS asks for:

> **fine-scale detail**

after transforming medium-resolution Sentinel-2 imagery into a higher-resolution product.

The naive interpretation is:

```text
10 m
 ↓
2.5 m
 ↓
sharper image
```

That is insufficient.

The scientifically correct interpretation is:

```text
10 m Sentinel-2 observation
        ↓
learned reconstruction
        ↓
2.5 m reconstructed grid
        ↓
additional spatial structure
```

The additional structure may include:

* edges
* boundaries
* textures
* small objects
* field boundaries
* water edges
* built-up boundaries
* vegetation patterns.

But Sentinel-2 did **not directly observe those details at 2.5 m**.

Therefore:

> **FRAME reconstructs fine-scale information; it does not recover an original 2.5 m observation that Sentinel-2 possessed.**

This wording should remain throughout the project.

---

# 2. The fundamental SR problem

A 10 m pixel can contain multiple materials.

For example:

```text
10 m pixel
┌────────────────────┐
│ vegetation │ road  │
│ vegetation │ road  │
│ vegetation │ road  │
└────────────────────┘
```

Sentinel-2 observes an aggregated response.

The SR model tries to infer:

```text
2.5 m
┌────┬────┬────┬────┐
│veg │veg │road│road│
├────┼────┼────┼────┤
│veg │veg │road│road│
├────┼────┼────┼────┤
│veg │veg │road│road│
├────┼────┼────┼────┤
│veg │veg │road│road│
└────┴────┴────┴────┘
```

But many different HR configurations can produce similar 10 m observations.

That means the inverse problem is **ill-posed**.

The model has to use learned priors.

And that is exactly where hallucination becomes possible.

---

# 3. Three fundamentally different outcomes

Modern SR evaluation provides an excellent framework.

## A. Improvement

The model generates high-frequency detail that actually corresponds to the HR reference.

```text
LR:    ─────────────
SR:    ──████████───
HR:    ──████████───
```

Good reconstruction.

---

## B. Omission

The HR reference contains detail but the model fails to reconstruct it.

```text
LR:    ─────────────
SR:    ─────────────
HR:    ──████████───
```

The model is conservative.

---

## C. Hallucination

The SR model generates detail that doesn't exist in the HR reference.

```text
LR:    ─────────────
SR:    ──████████───
HR:    ─────────────
```

This is the dangerous case.

OpenSR-Test explicitly measures hallucination, omission and improvement separately. ([GitHub][2])

---

# 4. Why "sharpness" is a dangerous objective

Consider two models.

### Model A

```text
Very sharp
Many edges
High texture
```

### Model B

```text
Moderately sharp
Less texture
Better physical agreement
```

A conventional visual metric or human observer might prefer A.

But if A generates false roads/buildings/field boundaries, it could be substantially less useful for geospatial analysis.

This is why recent SEN2SR research explicitly discusses the trade-off between generating high-frequency information and preserving physically meaningful content. ([DOI][1])

---

# 5. Existing solution — conventional CNN SR

Traditional reconstruction networks generally optimize something like:

```text
L1 / L2 reconstruction loss
```

Conceptually:

```text
L = |SR - HR|
```

This tends to produce conservative reconstructions.

The advantage:

> Less incentive to generate arbitrary detail.

The disadvantage:

> Fine detail can be averaged away.

SEN2SR's discussion specifically notes that pixel-level losses can favour **omission** over hallucination. ([DOI][1])

---

# 6. Existing solution — GAN SR

GANs introduce a perceptual/adversarial objective.

Conceptually:

```text
Generator
     ↓
realistic-looking HR
     ↑
Discriminator
```

This encourages sharper textures.

But there is a trade-off.

The model can generate details that are statistically plausible without being physically correct.

SEN2SR explicitly identifies GAN-based approaches as more prone to introducing high-frequency hallucinations because adversarial losses reward perceptual realism rather than exact pixel-level correspondence. ([DOI][1])

---

# 7. Existing solution — diffusion

LDSR-S2 represents the probabilistic/generative direction.

Diffusion models can produce rich fine-scale detail and model uncertainty through multiple samples.

But the SEN2NEON benchmark reports that the diffusion-based S2SR-LD configuration introduces additional detail at a cost in physical consistency/hallucination behaviour. ([GitHub][3])

So:

> More expressive generative modelling does not automatically mean more correct detail.

---

# 8. Existing solution — SEN2SR

This is currently the most important solution for FRAME.

SEN2SR explicitly separates:

1. consistency
2. synthesis
3. correctness.

Its framework uses harmonized training data and a low-frequency hard constraint, while evaluating whether generated detail is actually correct. ([DOI][1])

This is almost exactly the conceptual framework FRAME needs.

Therefore:

> **Do not create another arbitrary "detail enhancement" architecture.**

Use SEN2SR as the primary baseline and investigate what happens when that reconstruction is taken into downstream analysis.

---

# 9. What "synthesis" actually means

OpenSR-Test defines synthesis as:

> the amount of high-frequency detail introduced by the SR model.

Its default implementation uses a distance between LR/SR/HR information, and a higher synthesis value indicates more introduced high-frequency structure. ([GitHub][2])

This is useful.

But:

> **Synthesis ≠ correctness.**

A model can have:

```text
High synthesis
+
High hallucination
```

which is not necessarily desirable.

---

# 10. The most important metric combination

For FRAME, don't report:

```text
Synthesis = 0.08
```

alone.

Report:

```text
Synthesis
Hallucination
Omission
Improvement
Spectral consistency
Spatial consistency
```

together.

Conceptually:

```text
                    HIGH-FREQUENCY DETAIL
                            │
             ┌──────────────┼──────────────┐
             ▼              ▼              ▼
         Synthesis      Hallucination    Omission
             │              │              │
             └──────────────┼──────────────┘
                            ▼
                      Correctness
```

---

# 11. OpenSR-Test is directly useful here

OpenSR-Test was specifically created because conventional metrics such as:

* PSNR
* SSIM
* LPIPS

don't adequately characterize real-world Sentinel-2 SR.

It evaluates three independent dimensions:

### Consistency

Does SR remain compatible with LR?

### Synthesis

Did SR actually add useful spatial information?

### Correctness

Was that new information actually correct?

([GitHub][2])

This should become a core part of FRAME's benchmark.

---

# 12. Current benchmark evidence

The OpenSR-Test results demonstrate the trade-off very clearly.

For example, the current benchmark reports:

| Model         | Synthesis ↑ | Hallucination ↓ | Omission ↓ | Improvement ↑ |
| ------------- | ----------: | --------------: | ---------: | ------------: |
| LDSR baseline |      0.0285 |          0.6067 |     0.3088 |        0.0845 |
| OpenSR model  |      0.0068 |          0.3431 |     0.4593 |        0.1976 |
| Satlas        |      0.0227 |          0.8004 |     0.1073 |        0.0923 |
| SR4RS         |      0.0177 |          0.7274 |     0.1637 |        0.1089 |
| SuperImage    |      0.0046 |          0.2026 |     0.6288 |        0.1686 |

([GitHub][2])

Don't interpret these as a universal ranking.

The important lesson is:

> **Generating more detail can come with more hallucination, while generating less detail can increase omission.**

There is no single scalar "sharpness" objective.

---

# 13. The FRAME research question

This gives us a much stronger research question:

> **How much fine-scale information can be reconstructed from Sentinel-2 while maintaining spectral/geospatial consistency and minimizing incorrect high-frequency detail?**

That is much more scientifically defensible than:

> "Can we make Sentinel-2 sharper?"

---

# 14. "Fine-scale detail" must be tied to a task

This is critical.

A road boundary is useful for:

```text
urban mapping
```

A crop boundary is useful for:

```text
agricultural monitoring
```

A water boundary is useful for:

```text
flood mapping
```

Therefore, FRAME should not treat all detail equally.

---

# 15. Proposed detail categories

I recommend dividing reconstructed information into:

### A. Structural edges

Examples:

* building boundaries
* roads
* water boundaries
* field edges.

### B. Textural detail

Examples:

* vegetation texture
* urban texture
* soil texture.

### C. Spectral sub-pixel structure

Mixed-pixel decomposition:

```text
vegetation
+
soil
+
built-up
```

### D. Object-level structures

Potentially:

* buildings
* roads
* small water bodies.

But this should only be claimed where independently validated.

---

# 16. Why sub-pixel land-cover mapping fits FRAME

This is where your existing architecture becomes much more coherent.

Instead of saying:

> "We reconstruct buildings at 2.5 m."

we can say:

> **"We investigate whether the reconstructed spatial structure improves sub-pixel land-cover characterization."**

For each 2.5 m cell:

```text
P(vegetation)
P(cropland)
P(built-up)
P(water)
P(bare)
```

This is much more scientifically defensible.

---

# 17. But there is an important trap

Suppose:

```text
SR:
      building-like pattern
```

and the classifier predicts:

```text
built-up = 0.92
```

That does **not** prove that a building exists.

It may simply be propagating the SR model's hallucination.

Therefore:

```text
SR
 ↓
classification
```

must not automatically be treated as:

```text
ground truth
```

---

The hierarchy should be:

```text

      ↓

      ↓

```

Not:

```text

 ↓
SR
 ↓
classification
 ↓

```

SEN2NEON and OpenSR-Test are useful precisely because they provide independent HR references. ([GitHub][3])

Therefore the important distinction is:

> **visual enhancement vs scientifically validated reconstruction.**

FRAME belongs in the second category.

# SIH26142 — FRAME

## REQUIREMENT 8 — UNCERTAINTY / ERROR AWARENESS

This is the requirement where FRAME's proposed direction becomes much more interesting, but also where we need to be **extremely precise with terminology**.

The original idea of:

> "Generate an uncertainty map alongside the SR image"

is **not novel by itself**.

LDSR-S2 already generates pixel-level uncertainty maps from multiple diffusion samples, and earlier work has used deep ensembles to quantify epistemic uncertainty for Sentinel-2 SR. ([IEEE Xplore][1])

So FRAME cannot claim:

> "We are the first Sentinel-2 SR system with uncertainty."

The potentially interesting contribution is instead:

> **Can an evidence/stability layer identify reconstructed regions where SR is likely to be unreliable, and does that information actually correlate with reconstruction errors and downstream analytical errors?**

That is the question we need to test.

---

# 1. Exact NTRO interpretation

The PS requires:

> **uncertainty/error awareness**

This should be interpreted as the system being able to communicate not only:

```text
"What did the SR model produce?"
```

but also:

```text
"How reliable is this reconstruction?"
```

For FRAME, that means the output should eventually contain:

```text
SR product
+
quality/error evidence
```

rather than presenting every reconstructed pixel as equally trustworthy.

---

# 2. First distinction: uncertainty vs error

These are **not the same thing**.

## Error

Error is the difference between prediction and a known reference.

For example:

```text id="q3jv8e"
SR NDVI = 0.61
Reference NDVI = 0.58

error = 0.03
```

You can calculate this when reference data exists.

---

## Uncertainty

Uncertainty describes how uncertain the model/system is about its prediction.

For example:

```text id="5x9xv0"
Prediction:
0.61

Possible model outputs:
0.57
0.60
0.61
0.62
0.66
```

There is substantial predictive variation.

But:

> **Uncertainty is not automatically equal to error.**

A model can be:

```text
low uncertainty + high error
```

because it is confidently wrong.

This distinction must be built into FRAME.

---

# 3. Three concepts FRAME should keep separate

I recommend using:

### 1. Reconstruction error

Measured against HR reference.

### 2. Predictive uncertainty

Intrinsic uncertainty of the model's output.

### 3. Model stability

Variation in output under controlled perturbations.

These should not be collapsed into one "confidence score" initially.

---

# 4. Aleatoric vs epistemic uncertainty

The established ML terminology is useful here.

## Aleatoric uncertainty

Uncertainty inherent in the observation/problem.

For example:

* sensor noise
* information lost by spatial sampling
* ambiguous mixed pixels
* atmospheric effects.

It cannot simply be removed by giving the model more training data.

---

## Epistemic uncertainty

Uncertainty arising from model limitations.

For example:

* insufficient training coverage
* unfamiliar land-cover structures
* geographic domain shift
* model parameter uncertainty.

The 2023 Sentinel-2 deep-ensemble study explicitly discusses epistemic uncertainty in SR and uses ensembles to quantify it. ([DOI][2])

---

# 5. Why single-image Sentinel-2 SR is inherently uncertain

Consider:

```text id="h2nqkk"
10m pixel
┌────────────────────┐
│ vegetation │ road  │
│ vegetation │ road  │
└────────────────────┘
```

The model has only the aggregated measurement.

It cannot directly observe the exact:

```text id="1z3lqp"
2.5m
┌──┬──┬──┬──┐
│? │? │? │? │
├──┼──┼──┼──┤
│? │? │? │? │
└──┴──┴──┴──┘
```

There may be multiple plausible HR configurations.

Therefore uncertainty is not merely a model defect.

It is inherent to the inverse problem.

This is one reason probabilistic SR is attractive.

---

# 6. Existing solution — deep ensembles

The 2023 DSen2 uncertainty work uses **weighted deep ensembles**.

Conceptually:

```text id="lkvkdr"
Same LR input
      │
 ┌────┼────┬────┐
 ▼    ▼    ▼    ▼
CNN1 CNN2 CNN3 CNN4
 │    │    │    │
 └────┴────┴────┘
         ↓
 output distribution
         ↓
 uncertainty
```

Different trained models produce slightly different predictions.

The spread becomes an estimate of epistemic uncertainty.

The authors also report that uncertainty can be connected to physical patterns and used for selective prediction. ([DOI][2])

### Advantage

Conceptually interpretable.

### Disadvantage

Multiple full models are expensive.

---

# 7. Existing solution — LDSR-S2

This is the most directly relevant competing approach.

LDSR-S2 uses latent diffusion conditioned on the LR Sentinel-2 image.

The probabilistic diffusion process generates multiple possible SR realizations.

The spread across samples produces a **pixel-level uncertainty map**. ([IEEE Xplore][1])

Conceptually:

```text id="i6c7p9"
LR Sentinel-2
      │
      ▼
LDSR-S2
      │
 ┌────┼────┬────┐
 ▼    ▼    ▼    ▼
SR1  SR2   SR3  SR4 ...
 └────┴────┴────┘
          ↓
   pixel distribution
          ↓
   uncertainty map
```

This is much more principled than simply saying:

> "The image looks uncertain."

---

# 8. What LDSR-S2 actually provides

The LDSR-S2 paper describes:

* 10 m → 2.5 m SR
* visible + NIR bands
* LR-conditioned latent diffusion
* pixel-level uncertainty
* uncertainty useful for downstream tasks such as land-cover classification and change detection. ([IEEE Xplore][1])

The OpenSR implementation explicitly provides an uncertainty-calculation workflow. ([GitHub][3])

Therefore:

> **LDSR-S2 is our direct baseline for uncertainty-aware SR.**

---

# 9. The cost of principled uncertainty

The problem is computation.

OpenSR reports generating multiple LDSR samples, for example around 10 samples, to estimate pixelwise uncertainty. It notes that this can increase computational cost by roughly **10–20×** depending on the workflow. ([ESA Φ-lab Network][4])

That creates an engineering trade-off:

```text
More samples
    ↓
better empirical distribution
    ↓
better uncertainty estimate
    ↓
much higher compute
```

For a large satellite scene, this matters considerably.

---

# 10. FRAME's proposed alternative: stability evidence

This is where our previous architecture can still make sense.

Instead of claiming:

> "We calculate true uncertainty."

we can initially calculate:

> **model-stability evidence.**

For example:

```text id="6bvlr9"
Original input
   │
   ├── normal inference
   ├── augmentation 1
   ├── augmentation 2
   ├── small perturbation
   ├── tile overlap variation
   └── other controlled perturbations
          ↓
    multiple SR outputs
          ↓
       variance
          ↓
    stability map
```

---

# 11. But TTA variance is not uncertainty

This is extremely important.

Suppose:

```text id="t0j8w7"
Prediction A = 0.61
Prediction B = 0.61
Prediction C = 0.62
```

Variance is low.

That tells us:

> The model is stable under these perturbations.

It does **not** tell us:

> The prediction is physically correct.

Therefore the terminology should be:

### Good

* model stability
* prediction variability
* stability evidence
* consistency under perturbation

### Avoid

* calibrated uncertainty
* probability of correctness
* confidence = 95%
* ground-truth confidence

unless we actually develop and validate a calibrated probabilistic method.

---

# 12. This distinction is critical for the PPT

Do not write:

> "FRAME provides uncertainty-aware SR."

That is potentially misleading because LDSR-S2 already does principled probabilistic uncertainty.

A safer statement is:

> **"FRAME provides model-stability evidence alongside reconstructed products to identify regions requiring additional scrutiny."**

After validation, we can potentially strengthen the wording.

---

# 13. The most important FRAME experiment

We need to test:

```text id="i7k5bg"
STABILITY
      ↓
does it correlate with
      ↓
ACTUAL ERROR?
```

Use an HR reference.

For every pixel:

```text id="s9o5vp"
stability score
+
actual SR error
```

Then calculate:

* Pearson correlation
* Spearman correlation
* error vs stability bins
* AUROC for high-error detection
* AUPRC for high-error detection.

---

# 14. Example

Suppose:

| Stability percentile | Mean SAM error |
| -------------------- | -------------: |
| 0–20% most stable    |          0.018 |
| 20–40%               |          0.021 |
| 40–60%               |          0.027 |
| 60–80%               |          0.035 |
| 80–100% least stable |          0.061 |

That would provide evidence that:

> model instability is associated with reconstruction error.

That is scientifically meaningful.

---

# 15. But suppose the result is:

| Stability percentile | Mean error |
| -------------------- | ---------: |
| 0–20%                |      0.031 |
| 20–40%               |      0.030 |
| 40–60%               |      0.031 |
| 60–80%               |      0.032 |
| 80–100%              |      0.030 |

Then our stability layer isn't useful in that form.

We should not manufacture a positive conclusion.

This experiment is therefore **falsifiable**, which is exactly what we want.

# 23. Error taxonomy for FRAME

I recommend creating a formal error taxonomy.

## E1 — Radiometric error

Wrong reflectance.

Measured with:

* RMSE
* MAE
* bias.

---

## E2 — Spectral error

Wrong spectral relationships.

Measured with:

* SAM
* ERGAS
* index deviation.

---

## E3 — Spatial error

Wrong position/geometry.

Measured with:

* spatial consistency
* edge displacement
* registration metrics.

---

## E4 — Hallucination

Generated detail absent in reference.

---

## E5 — Omission

Reference detail not reconstructed.

---

## E6 — Domain-shift error

Performance degradation in unfamiliar geography.

---

## E7 — Model instability

Output changes substantially under controlled perturbations/sampling.

| Deep ensemble      | Model/epistemic variation      |      High | More defensible         |

| TTA/stability      | Sensitivity to perturbations   |  Moderate | No                      |
| Single prediction  | Nothing                        |       Low | No                      |

The critical conclusion:

> **FRAME's initial stability map should not be marketed as equivalent to LDSR-S2 uncertainty.**

# SIH26142 — FRAME

## REQUIREMENT 9 — ACCURACY ASSESSMENT & VALIDATION

This requirement is the point where the entire FRAME proposal either becomes scientifically credible or falls apart.

Up to Requirement 8, we established that:

* SR itself is already solved to a substantial degree.
* 2.5 m reconstruction already exists.
* spectral consistency already exists.
* spatial consistency already exists.
* hallucination/omission evaluation already exists.
* probabilistic uncertainty already exists.

Therefore, **we cannot differentiate FRAME merely by building another model**.

We need a validation framework that can answer:

> **Does the reconstructed product actually satisfy the NTRO requirements, and does its apparent improvement survive independent testing and downstream analysis?**

This is also where we need to be ruthless about what counts as evidence.

---

# 1. Exact NTRO interpretation

"Accuracy assessment" should not mean:

> "We calculated PSNR and SSIM."

That is insufficient for multispectral Earth observation.

FRAME needs to establish at least five different forms of validity:

```text
                  FRAME VALIDATION
                         │
        ┌────────────────┼────────────────┐
        ▼                ▼                ▼
   Reconstruction     Spectral         Spatial
      accuracy        fidelity         fidelity
        │                │                │
        └────────────────┼────────────────┘
                         ▼
                   Fine-detail
                   correctness
                         │
                         ▼
                Downstream utility
```

And Requirement 8 adds:

```text
                         +
                  error/stability
                     evidence
```

---

# 2. The validation hierarchy

I recommend that the final research document use this hierarchy:

## Level 0 — Engineering correctness

Does the output file itself make sense?

## Level 1 — Observation consistency

Does the SR product remain compatible with the original Sentinel-2 observation?

## Level 2 — HR reconstruction accuracy

Does it agree with an independent HR reference?

## Level 3 — Fine-detail correctness

Is the generated detail real rather than hallucinated?

## Level 4 — Spectral/geospatial analytical correctness

Do derived indices and spatial products remain valid?

## Level 5 — Downstream task performance

Does the SR product actually improve or preserve useful geospatial analysis?

## Level 6 — Generalization

Does it work outside the geographic distribution used during training?

That is the validation architecture FRAME should aim for.

---

# 3. Level 0 — Engineering validation

Before any ML metric, verify:

* CRS
* affine transform
* bounds
* pixel size
* dimensions
* band order
* nodata
* reflectance scaling
* metadata
* acquisition date
* source product
* model version.

For example:

```text
Expected:
resolution = 2.5 m
CRS = original projected CRS
bounds = original AOI
bands = expected FRAME bands
```

This should be automatically checked.

### Technology

**Rasterio + GDAL**

No research novelty here.

It is basic product integrity.

---

# 4. Level 1 — Observation consistency

This is one of the most important tests.

Take:

```text
FRAME 2.5 m output
        ↓
observation-grid reduction
        ↓
10 m equivalent
```

Then compare:

```text
10 m equivalent
       vs
original Sentinel-2
```

This is essentially the practical implementation of the consistency principle used by OpenSR-Test and SEN2SR. OpenSR-Test defines consistency as the requirement that the SR result, when degraded to LR scale, retains spectral and spatial fidelity with the LR input. ([ESA Φ-lab Network][1])

---

# 5. Why this test is mandatory

Without it, the model can cheat.

Example:

```text
Original S2:
reflectance = 0.30

SR:
beautiful texture
reflectance = 0.42
```

It might look impressive.

But after aggregation:

```text
SR → 10m
```

the result no longer matches the actual observation.

That violates the basic physical constraint.

---

### Spectral

* SAM
* ERGAS

### Structural

* PSNR
* SSIM

### OpenSR

* reflectance consistency
* spectral consistency
* spatial consistency.

This exact combination is also used in recent downstream Sentinel-2 SR evaluation. ([MDPI][2])

# 11. What counts as an acceptable FRAME result?

We should establish this **before** running the final experiments.

A useful success definition would be:

### Required

FRAME must not materially degrade:

* spectral consistency
* spatial consistency
* reflectance fidelity.

### Desired

FRAME should improve at least one of:

* fine-detail correctness
* downstream classification
* change detection
* stability/error detection.

### Strong result

FRAME improves downstream analytical utility **without materially sacrificing physical consistency**.

This is a much better definition of success than "PSNR increased."

# 12. Level 3 — Fine-detail correctness

### Consistency

### Synthesis

Does SR add high-frequency information?

### Correctness

Is the added information actually correct?

([OpenSR][4])

This directly addresses the problem we identified in Requirement 7.

# 13. Fine-detail metrics

Use:

### Synthesis

Higher = more high-frequency detail.

### Hallucination

Lower = better.

### Omission

Lower = better.

### Improvement

Higher = more correctly reconstructed new detail.

OpenSR-Test explicitly defines hallucination as detail in SR that isn't present in HR, omission as HR detail absent from SR, and improvement as newly recovered detail that is supported by HR. ([PyPI][5])

* geographic diversity
* held-out locations
* consistent preprocessing
* independent evaluation
* enough scenes.

Otherwise call it:

> **Indian-domain evaluation**

not:

> **India-optimized model**.

---

# 28. Statistical testing

This is currently missing from many student projects.

We should not just report:

```text
FRAME PSNR = 32.6
SEN2SR = 32.4
```

and declare victory.

Calculate confidence intervals.

For example:

```text
FRAME:
32.6 ± 0.3

SEN2SR:
32.4 ± 0.3
```

Then test whether the difference is statistically meaningful.

---

# 29. Recommended statistical approach

Because images/patches are spatially correlated, don't treat every pixel as an independent sample.

Use:

### Scene-level aggregation

Calculate metric per scene/tile.

Then compare model-level distributions across scenes.

Potential tests:

* paired bootstrap confidence interval
* Wilcoxon signed-rank test for paired scene-level results
* paired t-test if assumptions are justified.

Bootstrap is particularly useful for reporting uncertainty around mean differences.

---

# 30. Example

Suppose:

```text
FRAME:
mean PSNR = 32.5

SEN2SR:
mean PSNR = 32.2
```

But the 95% CI of the difference is:

```text
[-0.1, +0.7]
```

Then we cannot confidently claim improvement.

This is the kind of discipline the final research paper should have.

---

# 31. Effect size

Don't only report p-values.

Report:

> **How large is the difference?**

For example:

```text
ΔSAM = -0.004°
```

or:

```text
ΔIoU = +2.1 percentage points
```

A statistically significant but practically tiny improvement may not matter.

---

# 32. Confidence intervals

Every major metric should ideally have:

```text
mean ± standard deviation
```

and, for final comparisons:

```text
95% confidence interval
```

at the **scene/tile level**, not pretending millions of correlated pixels are independent observations.

---

# 33. Ablation testing

If FRAME introduces anything beyond SEN2SR, ablations become mandatory.

Suppose final FRAME has:

```text
A = SEN2SR baseline
B = + stability layer
C = + task-aware component
D = + domain adaptation
```

Run:

```text
A
A+B
A+B+C
A+B+C+D
```

Then identify which component caused the improvement.

---

# 34. Never do this

```text
Baseline:
random configuration

FRAME:
carefully tuned configuration
```

Then claim:

> "FRAME is better."

The comparison must control:

* training data
* test data
* preprocessing
* inference scale
* metrics
* hardware where relevant.

---

# 35. Resolution-specific validation

We also need to test whether performance differs by native band resolution.

For example:

### 10 m bands

B2/B3/B4/B8.

### 20 m bands

B5/B6/B7/B8A/B11/B12.

### 60 m bands

B1/B9, if we eventually reconstruct them.

This is critical.

The difficulty of:

```text
10m → 2.5m
```

is not equivalent to:

```text
20m → 2.5m
```

and definitely not:

```text
60m → 2.5m.
```

# 36. Important B1/B9 experiment

Current SEN2SR's full public pipeline focuses on 10 bands and does not reconstruct B1/B9 to 2.5 m.

FRAME's proposed 12-band output would therefore require explicit validation.

We should test:

```text
10-band
vs

```

rather than assuming:

> more bands = better.

### Option A

Keep them at their original resolution.

### Option B

Reconstruct them separately.

### Option C

Exclude them from the primary 2.5 m analytical product.

This is scientifically better than forcing a 12-band claim.

# 39. Validation of the stability layer

Requirement 8 gives another evaluation dimension.

For every pixel:

```text
stability
actual error
```

Then calculate:

### Spearman correlation

Does higher instability correspond to higher error?

### AUROC

Can stability identify high-error pixels?

### AUPRC

Useful if high-error pixels are rare.

### Risk-coverage curve

If we reject the least-stable pixels, does retained accuracy improve?

> The stability layer provides actionable selective prediction.

This is much stronger evidence than simply showing an uncertainty heatmap.


Not:

> "FRAME has the highest PSNR."

Instead:

### Strong result

```text
FRAME
≈ SEN2SR spectral/spatial fidelity

AND

FRAME
better downstream performance

AND

FRAME stability
predicts high-error regions

AND

```

That would align tightly with the entire project thesis.

# 43. What would constitute a weak result?

Suppose:

```text

+0.4 PSNR
```

but:

```text

spatial consistency worse
hallucination worse
downstream classification unchanged
```

Then:

> FRAME is not actually solving the intended problem.

We should report that honestly.

# 44. Acceptance criteria

I recommend defining three levels.

## Minimum

* Output passes geospatial integrity checks.
* No major spectral-consistency degradation.
* Competitive reconstruction metrics.
* No unacceptable hallucination increase.

## Target

* Competitive with SEN2SR.
* Strong spectral/spatial consistency.
* Better downstream analytical performance.
* Stability correlates with actual error.

## Research-grade success

* Target achieved across independent datasets.
* Improvement survives geographic holdout.
* Stability provides useful selective prediction.
* Results statistically supported.
* Ablations demonstrate why the system works.

unless we have a scientific basis for that exact threshold for our task.

The current benchmark values are useful reference points, not universal acceptance criteria. SEN2NEON itself reports distributions and model comparisons rather than defining one universal pass/fail threshold. ([GitHub][3])

Therefore:

> **Use relative benchmark performance initially.**

# SIH26142 — FRAME

## REQUIREMENT 10 — DOWNSTREAM ANALYTICAL USE

This is the requirement that should ultimately determine whether FRAME is more than an SR demonstration.

The question is no longer:

> "Can we make Sentinel-2 look like 2.5 m imagery?"

It is:

> **"Does the reconstructed product actually improve or preserve useful geospatial information when used for a real analytical task?"**

This distinction is now strongly supported by current research. A September 2026 OpenSR study evaluated Sentinel-2 SR directly for flood-water and burn-scar extraction and found that different SR models behave differently depending on the downstream task; stronger high-frequency response did not automatically produce better thematic results. ([MDPI][1])

That is almost exactly the problem FRAME should investigate.

---

# 1. Exact NTRO interpretation

The PS explicitly mentions use cases such as:

* crop monitoring
* urban analysis
* disaster assessment
* fine-scale geospatial analysis.

The important interpretation is:

```text
Sentinel-2
    ↓
Super-resolution
    ↓
Higher-resolution analytical product
    ↓
Actual geospatial task
```

The SR output is therefore not the final product.

It is an **intermediate analytical representation**.

For FRAME:

```text
S2 L2A
 ↓
preprocessing
 ↓
SR
 ↓
2.5 m reconstructed product
 ↓
indices / land-cover / change
 ↓
analysis
 ↓
evidence + quality flag
```

---

# 2. Existing industry solution

Commercial GIS systems already support downstream use of Sentinel-2 SR.

For example, ArcGIS now exposes the SEN2SR model specifically for producing 2.5 m Sentinel-2 imagery for:

* precision agriculture
* urban planning
* environmental monitoring
* disaster assessment
* classification
* segmentation
* change detection. ([ArcGIS][2])

Therefore:

> **"We can use SR imagery for GIS analysis" is not novel.**

The actual question is whether the SR product **improves the analytical result and remains trustworthy**.

---

# 3. Existing academic solutions

There are now several demonstrated downstream directions.

## A. Crop-field segmentation

A 2025 IGARSS study used ESRGAN-based Sentinel-2 10 m → 2.5 m SR for crop-field segmentation.

It evaluated:

* Fucino Plain, Italy
* Punjab, India
* Suzhou, China

and found that super-resolved imagery could support improved delineation of small/irregular agricultural fields, with further gains when models were trained specifically on super-resolved data. ([DOI][3])

This directly means:

> **Crop-field analysis is already an established SR downstream application.**

So FRAME cannot claim that simply applying SR to crop mapping is novel.

---

# 4. Crop-field boundary research is already more advanced

The SIDEST framework combines:

```text
Sentinel-2
 ↓
2.5m SR
 ↓
edge-corrected Segment Anything
 ↓
field boundaries
```

It was specifically designed for large-scale crop-field boundary delineation and evaluated using Sentinel-2 and PlanetScope. ([ScienceDirect][4])

So we should not build:

> "SR + segmentation = novelty."

That already exists.

---

# 5. Disaster mapping is also already demonstrated

The latest OpenSR spectral-use study evaluates:

### Flood

Using:

**MNDWI**

### Fire

Using:

**dNBR**

and compares multiple modern Sentinel-2 SR approaches. ([MDPI][1])

This is important because it directly tests whether SR helps a physically interpretable geospatial task.

---

# 6. What the latest study actually found

For the Valencia flood case:

Bilinear interpolation achieved approximately:

```text
F1 = 0.085
```

while LDSR-S2 reached approximately:

```text
F1 = 0.091
```

The improvement was therefore real but modest. ([MDPI][1])

This is extremely important for FRAME.

It demonstrates that:

> **"Sharper imagery" does not automatically produce dramatic downstream improvement.**

---

# 7. Boundary effects were much stronger

The same study found larger effects around hazard boundaries.

For flood mapping, learned SR models increased edge-region detections by roughly:

> **20–38%**

but this was accompanied by reductions in edge precision. ([OpenSR][5])

This gives us a very useful lesson:

```text
More detected boundary detail
        ≠
More correct boundary detail
```

Exactly the problem FRAME's evidence layer is intended to address.

---

# 8. Fire mapping showed model-dependent results

For burn-scar mapping:

* SWIN produced the strongest learned-model full-region agreement.
* LDSR-S2 performed particularly strongly in other task/edge measures.
* Mamba produced strong boundary behaviour.
* SRGAN generated more high-frequency content but also larger spectral deviations and boundary-distance increases. ([MDPI][1])

Therefore:

> **There is no universal "best SR model" for every downstream task.**

This supports our earlier decision not to define FRAME as simply "SEN2SR but better."

---

# 9. This changes how FRAME should define success

Bad definition:

> FRAME produces sharper imagery.

Better:

> FRAME produces a reconstructed product whose usefulness can be measured on specific geospatial tasks.

Best:

> **FRAME determines whether reconstructed fine-scale information improves downstream analytical performance without compromising spectral/spatial fidelity, and provides evidence when the reconstruction may be unreliable.**

That is the central requirement.

---

# 10. Recommended primary downstream task

We need to control scope.

I recommend:

## Primary

### Land-cover / sub-pixel land-cover mapping

Classes:

* built-up
* vegetation
* cropland
* water
* bare soil.

## Secondary

### Two-date built-up change/growth analysis.

These match the existing FRAME architecture and don't require us to build three separate application systems.

---

# 11. Why land-cover mapping?

Because it connects almost every previous requirement.

```text
SR
 ↓
spectral consistency
 ↓
spatial consistency
 ↓
fine-scale detail
 ↓
stability
 ↓
land-cover classification
```

It gives us a measurable downstream endpoint.

---

# 12. Why not start with object detection?

Because object detection would introduce another major research problem.

For example:

```text
building detection
road detection
vehicle detection
```

would require:

* specialized datasets
* object-level labels
* detection architecture
* detection metrics.

That distracts from the actual SR research question.

Land-cover mapping is much more naturally tied to multispectral Sentinel-2.

---

```text
       ↓

       ↓
```

---

# 14. What should the feature stack contain?

# Requirement 11 — Operationalisation, GIS-Ready Product Generation & System Deployment

This requirement is where FRAME stops being only a research model and becomes an **actual usable geospatial processing system**.

The important distinction is:

> **The SR model is not the product. The product is the complete, georeferenced, traceable, analysable output produced by the SR pipeline.**

A technically strong SR model that produces a TIFF with lost CRS, incorrect affine transform, patch seams, missing provenance, or no practical way to inspect the result would be a poor operational system.

---

## 11.1 Requirement

### NTRO requirement interpreted technically

The system should take Sentinel-2 imagery and produce a **usable super-resolved geospatial product**, rather than merely outputting an image tensor.

The operational system therefore needs to handle:

1. Sentinel-2 input discovery/acquisition
2. L2A preprocessing
3. band harmonisation
4. large-scene tiling
5. SR inference
6. overlap handling
7. reconstruction/stitching
8. preservation of geospatial reference
9. spectral/spatial validation
10. stability/evidence generation
11. analytical products
12. export
13. visualization
14. provenance
15. API access
16. batch processing
17. computational resource management

The actual workflow should be:

```text
Sentinel-2 L2A
      ↓
Input validation
      ↓
Preprocessing / masking / harmonisation
      ↓
Large-scene tiling
      ↓
SR model inference
      ↓
Overlap blending / border handling
      ↓
2.5 m reconstructed grid
      ↓
Geospatial reconstruction
      ↓
Spectral + spatial validation
      ↓
Model-stability evidence
      ↓
Downstream analysis
      ↓
 ┌───────────────┬────────────────┬──────────────────┐
 ↓               ↓                ↓
GeoTIFF/COG      Analytical       Web/API
                 products          access
```

---

# 11.2 What existing systems already solve

Operationalisation is **not an unexplored problem**.

This is particularly important because ESA's OpenSR ecosystem already contains a substantial portion of the infrastructure FRAME would otherwise have to reinvent.

---

## 11.3 Existing solution — ESA OpenSR / SEN2SR

ESA OpenSR provides not only models but also tooling around large-image inference.

The current SEN2SR package explicitly supports processing large images by dividing them into overlapping tiles and reconstructing the result. The documented `predict_large` workflow handles fixed-size model inputs, overlapping patches and reconstruction of the complete image. ([GitHub][1])

This matters because a real Sentinel-2 scene is much larger than a neural network's normal training patch.

### Existing approach

```text
Large S2 image
       ↓
128 × 128 LR patches
       ↓
SR model
       ↓
512 × 512 SR patches
       ↓
overlap
       ↓
reconstruct
       ↓
large SR image
```

SEN2SR explicitly introduces overlap to reduce tile-boundary artifacts. ([GitHub][1])

### OpenSR Utils goes further

The `opensr-utils` package provides:

* patch extraction
* configurable window size
* overlap
* border elimination
* weighted blending
* georeferenced output
* CPU inference
* GPU inference
* multi-GPU inference
* `.SAFE` input
* GeoTIFF input
* batch execution
* logging

It specifically describes weighted overlapping patches as a mechanism for reducing patch artifacts. ([GitHub][2])

Therefore:

> **Large-image SR inference is already solved in the OpenSR ecosystem.**

FRAME should reuse the concept rather than claiming tiled inference itself as novelty.

[ESAOpenSR SEN2SR](https://github.com/ESAOpenSR/SEN2SR?utm_source=chatgpt.com)
[OpenSR Utils](https://github.com/ESAOpenSR/opensr-utils?utm_source=chatgpt.com)

---

# 11.4 Existing solution — LDSR-S2 operational pipeline

The LDSR-S2 ecosystem also separates:

**model inference**

from

**real-world geospatial processing**.

The raw LDSR-S2 repository itself performs tensor-level inference, while `opensr-utils` is recommended for real Sentinel-2 processing. The utility handles tiling, overlap blending, stitching, CRS/transform preservation and georeferenced output. ([GitHub][3])

This is a very useful architectural lesson for FRAME:

> **Do not put geospatial I/O, tiling, model inference, validation and API logic into one giant Python script.**

Separate them.

# 11.5 Industry solution — ArcGIS

Esri has integrated Sentinel-2 super-resolution capability into ArcGIS through its pretrained SEN2SR model.

This is important because it demonstrates that SR is already moving beyond academic notebooks toward GIS-oriented workflows.

The industry direction is therefore:

```text
Satellite imagery
      ↓
SR
      ↓
GIS
      ↓
classification
segmentation
change detection
mapping
```

rather than:

```text
Satellite imagery
      ↓
SR
      ↓
look at pretty image
```

That supports FRAME's decision to make downstream analytical usefulness part of the system rather than an optional demo.

# 11.6 GIS-ready output

FRAME should not simply save:

```text
output.png
```

The primary output should be a **georeferenced multi-band raster**, preferably a Cloud Optimized GeoTIFF.

### Recommended primary output

```text
FRAME_SR_<scene_id>_<date>.tif
```

with:

* CRS
* affine transform
* bounds
* width
* height
* 2.5 m output resolution
* band descriptions
* nodata information
* scale/offset where applicable
* acquisition date
* source Sentinel-2 product ID
* model name
* model version
* preprocessing version
* processing timestamp
* SR factor
* provenance information

# 11.7 Why COG?

Cloud Optimized GeoTIFF is particularly appropriate for the output layer.

GDAL provides native support for creating COGs, including appropriate overview generation and other preprocessing required for the format. ([GDAL][4])

COG is useful because a user does not necessarily need to download a huge entire raster merely to inspect a small region.

Conceptually:

```text
                 FRAME COG
                    |
        ┌───────────┼───────────┐
        ↓           ↓           ↓
      region A    region B    region C
        ↓           ↓           ↓
     retrieve    retrieve    retrieve
     required    required    required
      pixels       pixels      pixels
```

This becomes particularly useful for web visualization.

# 11.8 STAC-based provenance

FRAME should also generate a STAC-style metadata record for each processed product.

STAC is specifically designed to provide standardized metadata and searchable descriptions for spatiotemporal geospatial assets. Its core structures include Items, Catalogs, Collections and APIs. ([STAC Specification][5])

For FRAME:

```text
STAC Item
│
├── source Sentinel-2 asset
├── FRAME SR COG
├── uncertainty/stability COG
├── land-cover output
├── change output
├── metadata
└── processing provenance
```

This gives FRAME a much stronger operational structure than putting everything into a custom JSON file.


```text

```

```text

```

### NDBI

```text

```

### Stability

```text

```

The user can switch between them without generating separate permanent images.

# 11.15 Asynchronous processing is important

SR inference should **not** necessarily be a blocking HTTP request.

Bad architecture:

```text
POST /superresolve
      ↓
HTTP connection waits
      ↓
GPU processes giant scene
      ↓
20 minutes later
      ↓
response
```

Better:

```text
POST /jobs
    ↓
job_id returned
    ↓
worker queue
    ↓
GPU inference
    ↓
validation
    ↓
COG generation
    ↓
analysis
    ↓
completed
```

Then:

```text
GET /jobs/{job_id}
```

returns:

```json
{
  "status": "processing",
  "progress": 63
}
```

This becomes important as scene size increases.

FastAPI's deployment documentation also highlights an important operational issue: separate server processes can each load their own copy of a machine-learning model, increasing RAM requirements. ([FastAPI][7])

Therefore, simply saying:

> "We will run four API workers"

is not automatically better for a GPU-heavy model.

# 11.17 Exact tiling strategy

This is one of the most technically important implementation details.

Suppose:

```text
LR tile = 128 × 128
SR factor = 4
```

Then:

```text
128 × 128 LR
        ↓
512 × 512 SR
```

But independent tiles can produce seams.

Therefore:

```text
          overlap
      ←────────────→
   ┌──────────────────┐
   │     tile A       │
   │                  │
   └────────┬─────────┘
            │ overlap
      ┌─────┴──────────┐
      │     tile B     │
      │                │
      └────────────────┘
```

FRAME should use:

* overlapping windows
* weighted blending
* border trimming where necessary
* deterministic stitching
* edge artifact checks

This is already used in OpenSR's operational tooling. ([GitHub][2])

Therefore the novelty is **not** the overlap algorithm.

---

# 11.18 A requirement that FRAME can add

Although tiling itself is solved, FRAME can add an **evidence check on tile boundaries**.

For every stitched region:

```text
left tile
    ↓
overlap
    ↓
right tile
```

calculate:

* spectral difference
* gradient discontinuity
* edge discontinuity
* stability difference

If:

```text
seam_error > threshold
```

flag it.

This could produce:

```text
Tile seam quality:
PASS
PASS
PASS
WARNING
PASS
```

This is much more aligned with FRAME's philosophy than simply implementing another stitching algorithm.

A real NTRO-style system may need to process multiple scenes.

Therefore support:

```text

Scene 2 → job 002
Scene 3 → job 003
Scene 4 → job 004
```

with:

```text
queued
 ↓
preprocessing
 ↓
inference
 ↓
validation
 ↓
analysis
 ↓
complete
```

A batch manifest could look conceptually like:

```csv
scene_id,aoi,date,model,output
S2A_001,Chennai,2026-01-10,SEN2SR-Mamba,COG
S2A_002,Chennai,2026-02-12,SEN2SR-Mamba,COG
```

This is especially useful for the two-date change-analysis component.

# 11.21 What should NOT be permanently stored

Do not retain every temporary tile unless required.

For example:

```text
128 × 128 LR tiles
512 × 512 SR tiles
temporary masks
temporary arrays
```

can consume enormous storage.

Instead:

```text
Input
 ↓
temporary tiles
 ↓
stitch
 ↓
final COG
 ↓
delete temporary tiles
```

Keep intermediate tiles only when:

* debugging
* reproducibility testing
* failure recovery
* research experiments

```text
 ↓
```

# 11.32 Claims to avoid

Do **not** say:

> “FRAME is the first operational Sentinel-2 SR platform.”

Not defensible.

Do not say:

> “FRAME is the first GIS-integrated Sentinel-2 SR system.”

Not defensible.

Do not say:

> “Our API makes Sentinel-2 processing real-time.”

Unless you actually measure and define real-time.

Do not say:

> “FRAME provides uncertainty.”

Unless you use a properly justified uncertainty method.

Prefer:

> “model-stability evidence”

for the cheaper stability approach.

Do not say:

> “FRAME creates true 2.5 m imagery.”

Say:

> **“2.5 m reconstructed grid.”**

Do not say:

> “SR recovers previously unobserved ground truth.”

It reconstructs information inferred from the LR observation and learned priors.

# Requirement 12 — Multi-Sensor / Cross-Domain Generalisation, Robustness & Vendor Independence

This is the point where FRAME needs to answer a harder question than:

> “Does the model work on the dataset it was trained on?”

The real question is:

> **Does FRAME remain useful when the geographic region, land cover, acquisition date, reference sensor, or image characteristics change?**

For an NTRO-oriented system, this matters because a model that performs well only on its training distribution is not a robust geospatial processing system.

---

# 12.1 Requirement

The system should be capable of processing Sentinel-2 imagery from different:

* geographic regions
* dates
* land-cover types
* atmospheric conditions
* Sentinel-2 acquisitions
* reference datasets
* high-resolution sensors

without requiring the model to be retrained for every new location.

The requirement can therefore be decomposed into:

1. Geographic generalisation
2. Land-cover generalisation
3. Temporal generalisation
4. Cross-sensor validation
5. Cross-domain robustness
6. Out-of-distribution detection/evidence
7. Model portability
8. Failure detection
9. Reproducibility across scenes
10. Independence from one particular HR reference sensor

---

# 12.2 Exact interpretation

There are actually **three different kinds of generalisation** that should not be mixed together.

### A. Geographic generalisation

Training:

```text
Europe + USA
```

Testing:

```text
India
```

This asks:

> Does the model generalise geographically?

---

### B. Sensor/reference generalisation

Training:

```text
SEN2NAIP
```

Testing:

```text
SEN2NEON
SPOT
Venµs
```

This asks:

> Does the model work when the HR reference comes from a different sensor?

---

### C. Temporal generalisation

Training:

```text
2020–2023
```

Testing:

```text
2025–2026
```

This asks:

> Does the model remain useful for different acquisition dates and surface conditions?

These should be tested separately.

---

# 12.3 Existing academic solution — DSen2

This problem is not new.

The original DSen2 work explicitly trained using data sampled from a wide range of geographical locations, climate zones and land-cover types, with the objective of producing a network that could generalise to arbitrary Sentinel-2 imagery without retraining. ([ScienceDirect][1])

This establishes an important precedent:

> **Global geographic training/generalisation is already an established research objective in Sentinel-2 SR.**

Therefore:

> “Our model works on multiple regions.”

is not itself novelty.

---

# 12.4 Existing modern solution — SEN2SR

The current ESAOpenSR ecosystem takes generalisation considerably further.

SEN2SR is evaluated using multiple independent datasets and cross-sensor references rather than relying exclusively on one synthetic training distribution. The RSE paper describes OpenSR-Test datasets involving SPOT, Venµs, NAIP and Spanish aerial imagery, with independent sensors used to evaluate models outside their training data. ([DOI][2])

This is much more scientifically meaningful than simply randomly splitting a dataset.

---

# 12.5 Why random train/test splitting is dangerous

Suppose SEN2NAIPv2 contains:

```text
Scene A
 ├── patch 1
 ├── patch 2
 ├── patch 3
 ├── patch 4
 └── patch 5
```

If we randomly split:

```text
TRAIN:
patch 1
patch 2
patch 4

TEST:
patch 3
patch 5
```

the model may effectively see almost the same geographic scene during training.

That produces a misleadingly optimistic result.

---

# 12.6 FRAME's split strategy

The split should therefore be:

```text
                 ALL DATA
                    │
          ┌─────────┴─────────┐
          │                   │
      TRAIN REGION        HELD-OUT REGION
          │                   │
    many scenes             unseen scenes
          │                   │
    training               final test
```

Prefer:

### Training

SEN2NAIPv2

### Validation

SEN2VENµS + SEN2NAIPv2 cross-sensor

### Final independent testing

SEN2NEON + OpenSR-Test

### Indian geographic test

Separate geographically held-out Indian Sentinel-2 scenes.

---

# 12.7 SEN2NEON changes the situation

SEN2NEON is particularly important for FRAME.

The current dataset contains:

* 2,269 spatially aligned tiles
* 119 NEON acquisition assets
* 110 dates
* 2018–2024 coverage
* 12 Sentinel-2-equivalent bands
* canonical 2.5 m HR reference
* multiple land-cover categories
* original Sentinel-2 L2A observations
* AVIRIS-NG-derived HR reference. ([GitHub][3])

This means FRAME can perform a genuinely independent test without creating its own massive validation dataset.

---

# 12.8 Cross-sensor validation

This is one of the most important concepts.

Suppose:

```text
TRAIN
S2 → NAIP
```

Then testing against:

```text
S2 → NAIP
```

only answers:

> Can the model reproduce its training reference ecosystem?

Testing against:

```text
S2 → AVIRIS-NG-derived S2-equivalent
```

asks a harder question.

Similarly:

```text
S2 → SPOT
```

or:

```text
S2 → Venµs
```

tests whether conclusions survive a different reference sensor.

OpenSR-Test was explicitly designed around this problem and includes multiple real-world cross-sensor datasets. ([GitHub][4])

---

# 12.9 Existing benchmark evidence

OpenSR-Test evaluates more than PSNR/SSIM.

It includes dimensions such as:

* reflectance consistency
* spectral consistency
* spatial consistency
* synthesis
* hallucination
* omission
* improvement

and even semantic measures using models such as RemoteCLIP. ([GitHub][4])

This is extremely relevant to FRAME.

It means:

> **Cross-domain testing should not simply report PSNR.**

A model may retain acceptable PSNR while producing problematic high-frequency details or spectral deviations.

---

# 12.10 Industry solution

Modern operational SR systems increasingly treat the model as a **pretrained general-purpose processor**, rather than training a completely new model for every geographic location.

The ESAOpenSR WebGIS, for example, demonstrates Europe-scale 2.5 m super-resolved Sentinel-2 imagery rather than a single small research scene. ([OpenSR][5])

ArcGIS also packages pretrained Sentinel-2 SR capability into a GIS workflow.

Therefore FRAME should follow:

```text
pretrained/general model
        ↓
new region
        ↓
validation
        ↓
evidence
```

rather than:

```text
new region
 ↓
collect dataset
 ↓
retrain
 ↓
hope it works
```

---

# 12.11 Indian solution

India already has substantial remote-sensing infrastructure and Sentinel-related EO access through ISRO/NRSC.

There is also published Indian research involving super-resolution of Sentinel-2 and Resourcesat/LISS-4 data.

Therefore the defensible research position is **not**:

> “No Indian work exists.”

Instead:

> **“FRAME explicitly evaluates geographic transfer to Indian scenes as an independent generalisation problem.”**

That is much stronger scientifically.

---

# 12.12 The Indian-domain experiment

This should become one of FRAME's strongest experiments.

### Training

Do not include the final Indian test locations.

```text
SEN2NAIPv2
+
SEN2VENµS
```

### Validation

```text
SEN2NEON
OpenSR-Test
```

### Final Indian test

```text
Indian Sentinel-2 scenes
```

Ideally include geographically diverse areas:

```text
urban
agriculture
coastal
dry/barren
forest
water
mixed landscapes
```

Do not select only easy scenes.

---

# 12.13 Chennai-specific temptation

Because the team is based in Chennai, there is a temptation to use:

```text
Chennai
Chengalpattu
Kanchipuram
```

for all validation.

That would be useful as a **demonstration**, but not sufficient as proof of Indian generalisation.

A stronger structure is:

```text
TRAIN
non-Indian datasets

       ↓

TEST
multiple Indian geographic regions
```

If only Tamil Nadu data is available, describe it as:

> **Tamil Nadu geographic holdout**

not:

> **India-wide generalisation**

---

# 12.14 Temporal robustness

A model can work geographically but still fail under temporal change.

For example:

```text
January
dry crop field
```

versus:

```text
August
dense vegetation
```

The underlying location is identical but its spectral/spatial appearance is very different.

Therefore:

```text
same location
different date
```

should be included in testing where possible.

---

# 12.15 Temporal experiment

Select:

```text
Date A
Date B
Date C
```

for the same AOI.

Run:

```text
S2(A) → SR(A)
S2(B) → SR(B)
S2(C) → SR(C)
```

Evaluate:

* spectral consistency
* stability
* reconstruction metrics where HR exists
* land-cover classification
* change analysis

The key question becomes:

> Does FRAME produce stable behaviour when the underlying landscape changes naturally?

---

# 12.16 Seasonal effects

For agricultural areas, test:

```text
cropping season
↓
harvest
↓
fallow
```

because spectral distributions change substantially.

A model should not be declared unreliable merely because the scene is different from training.

Instead, the evidence layer should help distinguish:

```text
legitimate scene variation
```

from:

```text
model failure
```

---

# 12.17 Atmospheric / acquisition robustness

Potential variation includes:

* haze
* thin clouds
* illumination
* aerosol effects
* scene brightness
* surface moisture
* cloud shadows
* mixed pixels

SCL masking should already remove many invalid pixels, but valid pixels can still vary substantially.

Therefore FRAME should retain:

```text
scene quality metadata
```

rather than silently treating every acquisition as equivalent.

---

# 12.18 Robustness should not mean “works on everything”

This is an important scientific distinction.

A good system does **not** need to produce a confident output for every possible input.

Instead:

```text
GOOD INPUT
   ↓
SR
   ↓
HIGHER TRUST

DIFFICULT INPUT
   ↓
SR
   ↓
FLAG / LOWER EVIDENCE
```

That is much more consistent with FRAME's philosophy.

---

# 12.19 Out-of-distribution detection

This is a possible research extension.

Given a new scene:

```text
TRAIN DISTRIBUTION
        │
        │
        ↓
New Sentinel-2 scene
        │
        ↓
Distribution similarity
        │
        ├── similar → normal processing
        │
        └── unusual → evidence flag
```

Possible signals:

* spectral distribution distance
* feature-space distance
* model activation statistics
* stability variance
* reconstruction residual
* land-cover mismatch

However:

**do not build a giant OOD research project unless time permits.**

---

# 12.20 Model activation as an evidence signal

This is particularly interesting because the current SEN2SR work reports a correlation between model performance and pixel-level model activation. ([ScienceDirect][6])

That means the model's internal response may contain information about where reconstruction quality varies.

This is highly relevant to FRAME's evidence-layer direction.

But:

> correlation ≠ validated uncertainty.

Therefore the correct terminology remains:

**model-stability / model-response evidence**

unless properly calibrated.

---

# 12.21 Potential FRAME extension

For every pixel or tile:

```text
SR output
+
spectral residual
+
spatial residual
+
model stability
+
OOD indicator
```

could produce:

```text
FRAME Evidence Score
```

But I would **not** immediately combine everything into one arbitrary 0–100 score.

That creates a scientifically questionable composite.

Instead preserve separate layers:

```text
spectral_error
spatial_error
stability
ood_indicator
```

and let the user interpret them.

# 12.25 Geographic degradation curve

One particularly useful FRAME experiment would be to evaluate performance by domain distance.

For example:

```text
Training-like region
       ↓
near domain
       ↓
different climate
       ↓
different continent
       ↓
India
```

Plot:

```text
Domain difference
        vs
SR error
        vs
stability
```

The question becomes:

> Does model-stability evidence increase when actual reconstruction quality degrades?

If yes, this becomes scientifically interesting.

---

# 12.26 Stability/error relationship

This is potentially more important than simply saying:

> “Our model works in India.”

Suppose:

```text
Region A
actual error = low
stability = high

Region B
actual error = high
stability = low
```

Then stability could potentially act as a useful screening mechanism.

Test this quantitatively.

### Correlation

```text
Spearman(stability, actual error)
```

### High-error detection

```text
AUROC
AUPRC
```

### Selective prediction

```text
coverage
risk
```

Example:

```text
Use only 90% most stable pixels
        ↓
Does reconstruction/downstream error decrease?
```

That would be a meaningful FRAME experiment.

---

# 12.27 Risk-coverage experiment

This is one of the strongest possible experiments for the project.

Sort pixels/tiles by:

```text
model stability
```

Then progressively retain:

```text
100%
90%
80%
70%
...
```

Measure error.

Ideal behaviour:

```text
Coverage ↓
Risk ↓
```

Conceptually:

```text
        Error
          │
          │\
          │ \
          │  \
          │   \
          │    \____
          └────────────
             Coverage
```

If stable regions genuinely correspond to lower reconstruction error, FRAME can make a stronger claim about **quality-aware usage**.

If there is no relationship, that is also a scientifically valuable negative result.

# 12.28 Multi-sensor does NOT mean merging sensors into one model

Avoid unnecessary complexity.

You do not need:

```text
Sentinel-2
+
SPOT
+
NAIP
+
WorldView
+
Planet
```

as model inputs.

For FRAME, these are primarily:

> **independent validation/reference sources.**

The operational input remains:

**Sentinel-2.**

This keeps the architecture aligned with PS26142.

# 12.29 Vendor independence

“Vendor independence” needs careful wording here.

Sentinel-2 itself is operated by the European Copernicus programme, so FRAME is inherently built around a specific satellite mission.

What can be made independent is:

* reference HR sensor
* data provider/API
* storage backend
* GIS software
* deployment environment

For example:

```text
Input:
Copernicus STAC
       OR
Bhoonidhi
       ↓
same FRAME processing
       ↓
same product
```

This is useful operationally.

But do not claim:

> “FRAME is satellite-vendor independent.”

That would be inaccurate.

# 12.30 Actual technical gap

The individual components are mature:

```text
global generalisation       → existing
cross-sensor validation     → existing
geographic testing          → existing
temporal testing            → established
OOD research                → established
stability analysis          → existing research
```

The less-explored combination is:

```text
geographic generalisation
        +
cross-sensor validation
        +
stability evidence
        +
downstream analytical utility
        +
operational GIS product
```

Therefore the FRAME research question becomes:

> **Can model-stability evidence identify regions where Sentinel-2 SR performance degrades under geographic, temporal or sensor-domain shift, and can that evidence be used to control or qualify downstream geospatial analysis?**

That is substantially more interesting than another architecture comparison.

# Requirement 12 conclusion

The important conclusion is:

**FRAME should not attempt to invent another “generalizable Sentinel-2 SR model.”**

That problem already has substantial literature, beginning with DSen2's global generalisation objective and extending to today's ESA OpenSR ecosystem. ([ScienceDirect][1])

Instead, FRAME should ask a more operationally useful question:

> **When the model encounters a new geography, date, land-cover distribution or reference domain, can its evidence layer indicate whether the resulting reconstruction remains suitable for downstream analysis?**

That connects Requirement 12 directly to Requirements 8–11:

```text
Requirement 4
SR reconstruction
       ↓
Requirement 5
spectral consistency
       ↓
Requirement 6
geospatial consistency
       ↓
Requirement 7
fine-detail correctness
       ↓
Requirement 8
model stability
       ↓
Requirement 9
validation
       ↓
Requirement 10
downstream analysis
       ↓
Requirement 11
GIS-ready operational product
       ↓
Requirement 12
generalisation / domain shift
       ↓
       ┌─────────────────────────┐
       │ FRAME's central idea   │
       │                         │
       │ "Can we know where     │
       │  the SR product needs  │
       │  more scrutiny?"       │
       └─────────────────────────┘
```

This is now becoming a coherent research story rather than 12 disconnected features.
